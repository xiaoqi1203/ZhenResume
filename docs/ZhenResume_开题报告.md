## 一、课题名称

**基于多 Agent 工作流与检索增强生成的智能简历诊断与优化系统（ZhenResume / 简甄）研究与实践**

---

## 二、选题背景与研究意义

### 2.1 现实痛点

在当前就业市场与招聘环境下，简历是求职者与招聘方之间的第一道信息闸门。现实中普遍存在三类问题：

1. **求职者侧**：大量简历存在经历无量化、ATS（Applicant Tracking System，申请人跟踪系统）不可解析、关键信息缺失、表述夸大或与 JD（Job Description，岗位描述）不匹配等问题，而求职者缺乏专业、即时、低成本的反馈渠道。
2. **HR 侧**：中小企业在无预算采购企业级 ATS 的情况下，初筛仍依赖人工逐份阅读，耗时从小时级到天级，效率低、标准不统一。近年研究开始系统评估大语言模型在招聘筛选环节的适用性[19]，并探索生成式人工智能在人才筛选中的应用边界[21]。
3. **工具侧**：市面上多数"简历打分器"只给出总分或泛泛建议，结论黑箱、不可追溯、不可执行；且自动化筛选还面临算法歧视的合规风险[15][16][17][18]。

### 2.2 研究意义

本课题旨在构建一套**证据化、可执行、工作流化**的简历诊断系统，核心价值在于：

- **证据化**：不黑箱打分，每条结论都能追溯到简历原文或 JD 原文，以缓解大模型事实性问题带来的信任风险[20]；
- **可执行**：直接给出可复制的改写句，而非"请加强量化"这类空泛建议；
- **工作流化**：将"解析 → 匹配 → 评分 → 风险 → 建议 → 质检 → 报告"标准化为可观测的多 Agent 流水线[6][22]；
- **越用越准**：用户反馈与人工修正沉淀为可复用的岗位知识资产[1][3]。

课题成果既能为个体求职者提供低门槛的自我诊断与改写辅助，也能为中小企业 HR 提供分钟级初筛能力，兼具学术探索价值与明确的工程落地价值。

## 三、国内外研究现状

### 3.1 文本解析与文档理解

简历与 JD 的解析涉及 PDF/DOCX/图片多种格式，学界在版面分析与 OCR 上已有成熟积累；中文简历解析方面，已有基于深度神经网络[7]、字序列建模[9]、BERT-BiGRU-CRF 命名实体识别[10]等研究，深度学习在简历信息抽取中的应用也已形成较完整的路线[8]。工程上仍普遍面临多栏排版错位、扫描件质量参差等问题，因此本系统采用"规则解析基线 + LLM 纠错兜底 + 可插拔 OCR"的务实组合，并以**逐字段合并**（LLM 字段为空时回落规则基线）避免模型"越改越少"。

### 3.2 大语言模型与检索增强生成

检索增强生成（Retrieval-Augmented Generation, RAG）通过外部知识检索缓解大模型的幻觉与知识时效问题，近年综述对 RAG 的概念、核心技术与挑战给出了系统梳理[1][4]，并有面向软件工程等垂直领域的应用综述[2]，以及针对检索增强优化的技术综述[3]。在事实性问题上，已有研究从评估、增强与展望三个层面综述大模型的事实性缺陷[20]。

值得注意的是，RAG 的检索质量高度依赖**向量表征与重排**，而非把所有问题都归因于生成端。本系统在 V1.0 阶段采用本地确定性哈希向量，V1.1 已升级为真实语义向量并保留"模型一致性守卫"（查询向量与库内向量非同源时退化为纯词面检索，绝不静默劣化），实测 12 条标注查询下 recall@3 达 100%、MRR 0.861。

### 3.3 多智能体编排与工作流

以 LangGraph、AutoGen、CrewAI 为代表的编排框架，使多步骤、有状态、可观测的工作流成为可能[22]；面向自然语言交互的模块化 AI 智能体工作流编排也已有系统研究[23]。多智能体协作在大语言模型驱动下形成了从"人机协作科学假设生成"[5]到"多循环嵌套指挥控制"[6]等多种形态。

本课题的编排路线经历了一次**有据可查的演进**：V1.0 以手写状态机替代重编排框架（理由：8 节点为确定线性链，无分支/循环/人机回环），并把节点签名刻意对齐 LangGraph 以便回退[22]；V1.1 已按该设计完成 **LangGraph 1.2 接入**，实现三路并行扇出（关键路径由 13.1s + 22.9s 压缩至 22.9s）、节点级可观测与 checkpoint 断点续跑，并以 **174 项端到端断言**锁定"替换前后行为等价"。这一"先契约、后替换"的做法本身即是对编排框架落地风险的一种工程回应。

### 3.4 人岗匹配与简历推荐

人岗匹配已有结合深度语义特征[11]、BERT 混合推荐[12]、端到端深度模型[13]、BERT + LightGBM[14]等多条技术路线。这些工作的共同假设是"匹配度可由语义相似度或统计模型估计"。本课题的观察是：在**有限算力与强可解释性要求**的中小企业场景下，纯相似度排序难以回答"为什么这个候选人不合适"，因此转向"证据化诊断"——不只给分数，还给可定位的原文依据与可执行改写建议。

### 3.5 公平性（Fairness）与合规

AI 简历评估天然存在性别、年龄、婚育等歧视性建议风险。法学界对算法雇佣决策下的隐蔽就业歧视[15]、自动化决策中的就业性别歧视[16]、就业算法歧视的法律规制[17]以及特征选择引发的歧视[18]已有系统讨论。本系统在产品原则层即明确"不输出歧视性内容"，并通过 `risk_agent` + `qc_agent` 双层拦截 + 正则硬过滤，把公平性检查通过率列为硬性验收指标（100%）。

### 3.6 研究空白与切入点

综合来看，现有研究在以下三点上仍显薄弱，构成本课题的切入点：

1. **可追溯到原文的逐条可执行建议**：多数系统输出分数或标签，缺少"改哪一句、改成什么"的可验证建议；
2. **确定性可回归的评分**：LLM 参与打分会导致同一输入多次输出不一致，使"改后对比分数变化"失效，而 HR 场景无法解释"为什么上周 A 第一本周 B 第一"；
3. **语义判断与确定性评分的融合机制**：规则层的关键词匹配无法理解项目上下文，会把"服务治理"与"微服务"这类同义表述误判为能力缺失。已有工作多在"纯规则"与"纯模型"之间二选一，缺少"语义判断经证据校验后进入确定性评分"的中间路线。

本课题的三个刻意设计——**评分不让 LLM 自由打分（确定性公式）**、**证据链不信任模型输出的位置（服务端重新定位引文）**、**语义判断必须携带可定位引文才能进入评分**——正是针对上述空白的切入点。

## 四、研究目标

1. 构建 60 秒内产出结构化诊断报告的端到端系统，覆盖"上传简历 → 解析 JD → 多 Agent 工作流 → 报告 → 二次诊断"完整链路。
2. 建立**确定性强、可回归**的五维评分模型，保证同一份简历多次诊断分数一致（支撑"改后对比分数变化"的核心卖点）。
3. 建立**可追溯证据链**，保证每条红色风险都有可定位的原文引用。
4. 建立**可降级**的 LLM 调用链（供应商×模型双层阶梯 + 重试 + 规则引擎兜底），实现零 API Key 也能产出契约合规的完整报告。
5. 提供面向求职者的简历模板与结构化编辑器，实现"不打开 Word 也能写简历并与诊断闭环打通"。
6.（V2.0 新增）建立**语义判定 Agent 与 Agentic RAG** 能力：让模型在受控预算内自主调用工具、自证证据，并把经硬校验的语义判断并入确定性评分，量化其相对纯规则与单次调用的增益。

   **实测结论（2026-10-17，详见 `ZhenResume_实测数据总表.md`）**：
   - 语义判定单次调用 + 工具：假差距 recall **88.9%**、证据定位 **100%**、真差距误判 **0%**，成本 ¥0.005/份；
   - 同一任务改用 LangChain Agent 循环：误判 **49→38（−22%）**、recall 90.3%，但排序相关性 **+0.847→+0.755**、成本 16×
     → 结论：**该子任务不需要 Agent 循环**（有效负面结论，已写入论文/答辩材料）；
   - **Agentic RAG（知识库证据 Agents）**：自主多轮检索（≤4 轮）+ 逐字引用校验，
     检索覆盖 gold 切片 **89.2%→93.3%**，"每条结论至少引到 1 条有效依据" **0%→100%**，引用逐字校验通过率 **97–99%**，成本 ¥0.094/份；
     并在此过程中修复了 `rag.search(role_family)` 硬过滤导致 `general` 类知识永久不可达的真实缺陷。

| 支付与订阅 | 免费/按次/月订阅/HR 套餐（MVP 为 Mock） |

| 管理后台 | 知识库维护、Prompt 模板版本化、反馈审核、成本监控、公平性检查[15][16] |
| 编辑器 | 4 套模板、结构化填写、实时预览、三格式导出、与诊断闭环打通 |

### 5.2 非功能需求

性能（单份 ≤60s，批量 100 份 ≤10min）、可用性（99.5% + 降级）、安全（HTTPS/加密/权限/审计）、隐私（可删除、默认不用于训练）、公平性（无歧视输出）[15]–[18]、可扩展（多模型/多语言/多行业）、成本（单份 API ≤0.5 元）、合规（明确"不构成录用/法律意见"）。

### 5.3 验收标准

- 上传简历 + JD 后 60 秒内生成报告；
- 报告含 ≥5 条可执行改写建议（不足时补**真实优点**，绝不编造问题）；
- 每条红色风险有原文引用与证据；
- 支付成功后报告可下载；用户可删除数据；
- 公平性检查通过率 100%；
- （V2.0 新增）语义判定满足：假差距识别 recall ≥80%、**证据定位通过率 ≥85%**、真差距误判率 ≤10%、同一输入重跑分数逐位一致。

## 六、关键技术问题与技术方案

### 6.1 核心链路设计

```
POST /resumes → 文本抽取 → 规则解析 → 存 raw_text + parsed_json
POST /jds     → 规则解析 → 技能/年限/学历/关键词
POST /tasks   → 202 立即返回 → 工作流启动
   └─ 工作流（每步落一行 workflow_steps：status/tokens/cost/latency）
        parse → jd_match → ats → impact → risk → suggestion → report → qc
        （并行版：jd_match 扇出 ats/impact/risk，merge 按固定顺序归并）
GET /tasks/{id}   → 轮询进度
GET /reports/{id} → 结构化报告
```

两个关键设计决策：① **质检（qc）会剔除或降级发现项，因此引擎在 qc 之后重算一次分数**，避免"总分与问题清单自相矛盾"；② **并行扇出后的归并顺序被固定**，否则发现项顺序会随调度抖动，导致回归断言不可复现[22]。

### 6.2 关键技术难点与对策

**难点一：评分必须可回归，不能"同一简历两次分数不同"。**
对策：五维评分（ATS 30% / 影响力 25% / 清晰度 20% / 竞争力差距 15% / 风险 10%）全部由确定性公式 `services/analyze.py` 计算，**只采纳规则层发现项**（`origin=rule`），LLM 自行增删的条目照常展示但不参与扣分。实测曾出现 risk 78 ↔ 95 的波动，正是该约束的由来。

**难点二：证据链不能信任模型输出的位置。**
对策：模型只输出引文（quote），字符区间由 `services/evidence.py` 在原文中三级重定位（精确 → 折叠空白 → 最长可定位前缀）；定位不到的红色风险被质检强制降级为黄色。

**难点三：LLM 调用必须可降级，不能"一挂全挂"。**
对策（两层阶梯 × 层内重试）：供应商阶梯（阿里云 → DeepSeek）× 同层模型阶梯，层内再做指数退避重试；**截断（`finish_reason=length`）与超时被识别为确定性失败，跳过重试直接换模型**（实测否则会出现"5 模型 × 3 次重试全被截断、239s 后降级"）；全部失败才回落该 Agent 的规则实现（标记 `degraded`，原因写进 notes，绝不静默）。仅 `parse`（critical）失败才终止任务。

**难点四：高质量简历不足 5 条问题时的"诚实"处理。**
对策：先补"简历确实缺失的检查项"，仍不够则补**真实存在的优点**（severity=green，附原文证据 + 面试用法），绝不编造问题。

**难点五：编辑器产出的简历不能与上传简历"分叉"。**
对策：`POST /resumes/from-editor` 把结构化内容渲染为纯文本存入 `raw_text`，使其在流水线中与上传简历完全等价，无特殊分支；代价是需保证渲染文本能被规则解析正确读回，并以断言锁定。

**难点六（V2.0 新增）：规则层的关键词匹配无法理解项目上下文。**
现象：JD 写"微服务/分布式/性能优化"，简历写"服务治理/多服务调用链路治理/P99 从 320ms 降至 90ms"，规则层会判为**能力缺失**，直接压低 ATS（权重 30%）与竞争力差距（15%）。实测某真实样例因此被低估 **15 分**（ATS 73，实际应为 88）。
对策：引入**语义判定**，但必须满足"可控、可校验、可回归"三个条件：
- **只出判断与证据，不出分数**：LLM 输出结构化判断（真差距/表述差异）+ **必须逐字复制的原文引文**；
- **服务端硬校验**：引文必须能被服务端在简历原文中定位（`locate_quote`），定位失败即作废；同一关键词只接受一条；不接受已被字面覆盖的项；
- **验后并入确定性评分**：通过校验的等价项计入关键词覆盖，评分公式与权重一行不改；
- **缓存保证可回归**：判定结果以 `(简历, JD)` 为键缓存（采样温度非 0，不缓存则重跑仍会有微差），使"同一输入两次诊断分数一致"继续成立。
- **分层加权**：JD 要求区分核心项 / 加分项 / 概念词（权重 1.0 / 0.6 / 0.3），修正"缺加分项与缺核心项等罚"的错配——实测发现加分项抽取存在缺陷（见 §11）。

**难点七（V2.0 新增）：如何证明"Agent 化"确有必要。**
对策：建立**可自动判定的评测夹具**（30 份，生成时即知每份的"真差距/表述差异"答案），对"单次调用"与"Agent 工具循环"两条引擎跑同一批样本，比较 recall / 证据定位通过率 / 误判率 / 成本 / 延迟。**若 Agent 循环不能带来可测增益，则不引入**——以数据而非技术偏好决定架构。

### 6.3 技术栈与 MVP-lite 取舍

## 八、本课题的创新点

1. **确定性强、可回归的评分模型**：五维评分拒绝 LLM 自由打分，保证"同一简历多次诊断分数一致"，让"改后对比分数变化"这一核心卖点真实可信。
2. **服务端重新定位的证据链**：不信任模型输出的字符区间，由服务端在原文中重定位引文，定位失败的红色风险强制降级，从机制上杜绝"虚构证据"。
3. **"语义判断经证据校验后进入确定性评分"的融合机制**（V2.0 核心创新）：语义判断只在**携带可通过服务端定位的原文证据**时才被允许影响评分，公式与权重保持不变——在不牺牲可回归性的前提下获得上下文理解能力。这与"纯规则"和"纯模型打分"两条既有路线都有区别。
4. **零 Key 可运行的降级架构**：双层阶梯 + 规则兜底，使系统在无 API Key 时仍能产出契约合规报告，降低演示、测试与冷启动门槛。
5. **"诚实补优点"的建议生成策略**：报告条数不足时不编造问题，而是补真实优点（green），兼顾验收标准与用户信任。
6. **契约冻结 + 实测驱动的工程纪律**：API 契约先行冻结，170+ 项端到端断言防止契约漂移；编排层替换（手写状态机 → LangGraph）以"替换前后断言全绿"为验收条件；Agent 化与否由评测数据决定而非技术偏好。
7. **可自动判定的评测夹具方法**：以"生成时即知答案"的夹具替代高成本人工标注，使语义判定与 Agent 增益可被自动化度量与回归。

## 十一、已知边界与下一步（诚实标注）

**V1.0 已标注且仍成立的边界**：真实登录鉴权缺失（`X-Device-Id` 可被伪造）、支付验签为 Mock、PDF 导出需本机 LibreOffice、OCR 依赖本机 tesseract、多栏排版可能错位、无 Alembic 迁移（`init_db()` 直接建表，导致现网库 schema 与模型漂移——实测 `resumes` 表缺 `file_sha256` 等列）、上传简历导出有损。

**V2.0 实测新增的边界（重要）**：

1. **JD 加分项抽取失效**：`parse_jd_text` 虽定义了加分项标题词表，但实测 7 个 JD 的 `skills_bonus` **全部为空**，导致"加分项权重"没有作用对象；
2. **`jd_match` 的语义纠错路径断线**：该 Agent 注释自称"唯一允许 LLM 推翻规则结论的地方"，但读取的字段名（`real_gaps_as_findings`）与提示词要求输出（`real_gaps`）不一致，**该分支在 live 模式下恒为空**；且即便修好字段名，覆盖率仍在评分函数中由子串匹配重算，**不影响分数**；
3. **`role_family` 过滤是死代码**：知识库该列有索引、取值也已算出，但检索函数从未接收该参数；
4. **评测样本受限**：现有真实简历去重后仅 9 份唯一文本，且多为测试夹具，因此评测改用生成夹具（30 份）；
5. **供应商额度**：`qwen3.8-max` 免费额度已耗尽（已从降级链移除，主模型调整为 `deepseek-v4-pro-0813`）；
6. **`suggestion`/`report`/`qc` 三个 Agent 职责存在重叠**：发现项的所有权在四处转移（追加 → 覆盖重写 → 定稿重算 → 质检删改），其中 `suggestion` 单文件 498 行，大部分逻辑用于维持"规则层不被 LLM 挤掉"这一不变量。

**建议下一步顺序**：① P0 修复加分项抽取与语义判断接入（含 `score_v2` 档位与回归断言）；② 建立 Agentic 新链路并跑对照实验；③ 换 PostgreSQL + pgvector 并为向量列建 HNSW 索引；④ 真实认证与支付验签；⑤ 接入 LLM 可观测（OpenTelemetry 或 Langfuse 私有部署，避免简历文本外发）。
