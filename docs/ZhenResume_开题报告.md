## 一、课题名称

**基于多 Agent 工作流与 RAG 知识库的智能简历诊断与优化系统（ZhenResume / 简甄）研究与实践**

---

## 二、选题背景与研究意义

### 2.1 现实痛点

在当前激烈的就业市场与招聘环境下，简历是求职者与招聘方之间的第一道信息闸门。然而现实中普遍存在三类问题：

1. **求职者侧**：大量简历存在经历无量化、ATS（申请人跟踪系统）不可解析、关键信息缺失、表述夸大或与 JD（岗位描述）不匹配等问题，但求职者缺乏专业、即时、低成本的反馈渠道。
2. **HR 侧**：中小企业在无预算采购企业级 ATS 的情况下，初筛仍依赖人工逐份阅读，耗时从小时级到天级，效率低、标准不统一。
3. **工具侧**：市面上多数"简历打分器"只给出总分或泛泛建议，结论黑箱、不可追溯、不可执行，用户拿到分数却不知道"具体改哪一句"。

### 2.2 研究意义

本课题旨在构建一套**证据化、可执行、工作流化**的简历诊断系统，其核心价值在于：

- **证据化**：不黑箱打分，每一条结论都能追溯到简历原文或 JD 原文，建立用户对系统的信任。
- **可执行**：直接给出可复制的改写句子，而非"请加强量化"这类空泛建议。
- **工作流化**：将"解析 → 匹配 → 评分 → 风险 → 建议 → 质检 → 报告"标准化为可观测的多 Agent 流水线。
- **越用越准**：用户反馈与人工修正可沉淀为可复用的岗位知识资产。

课题成果既能为个体求职者提供低门槛的自我诊断与改写辅助，也能为中小企业 HR 提供分钟级初筛能力，兼具学术探索价值与明确的工程落地价值。

## 三、国内外研究现状

### 3.1 文本解析与文档理解

简历与 JD 的解析涉及 PDF/DOCX/图片多种格式。学术界在文档版面分析（Layout Analysis）与 OCR 上已有成熟积累（如基于规则与深度模型的版面还原），但工程上仍普遍面临多栏排版错位、扫描件质量参差等问题。本系统采用"规则解析基线 + LLM 纠错兜底 + 可插拔 OCR"的务实组合，在 MVP 阶段优先保证主链路可用。

### 3.2 LLM  Agent 编排

以 LangGraph、AutoGen、CrewAI 为代表的 Agent 编排框架，使多步骤、有状态、可观测的工作流成为可能。本课题参考其思想，在 MVP 阶段采用**手写状态机**替代重编排框架（8 个节点为确定线性链，无需分支/循环/人机回环），将框架能力沉淀为"可回退的替换点"，体现"先落地、后升级"的工程权衡。

### 3.3 检索增强生成（RAG）

RAG 通过"知识库切片 → 向量化 → 混合检索 → 引用来源"缓解大模型的幻觉问题。现有方案如 LlamaIndex 提供了较完整的索引与重排能力。本系统在 MVP 阶段实现自研切片 + 混合检索（0.6 向量 + 0.4 词面），并将 embedding 设计为"本地确定性向量"这一可升级点，为后续接入真实语义向量（bge-m3 / text-embedding-3-small）预留空间。

### 3.4 公平性（Fairness）与合规

AI 简历评估天然存在性别、年龄、婚育等歧视性建议风险。学术界对算法公平性与招聘合规已有大量研究。本系统在产品原则层即明确"不输出歧视性内容"，并通过 `risk_agent` + `qc_agent` 双层拦截，将公平性检查通过率作为硬性验收指标（100%）。

### 3.5 研究空白与切入点

现有工具在"可追溯到原文的逐条可执行建议"与"确定性可回归的评分"上普遍薄弱。本课题的两个刻意设计——**评分不让 LLM 打分（确定性公式）**与**证据链不信任模型输出的位置（服务端重新定位引文）**——正是针对这一空白的切入点。

## 四、研究目标

1. 构建一个 60 秒内产出结构化诊断报告的端到端系统，覆盖"上传简历 → 解析 JD → 8-Agent 工作流 → 报告 → 二次诊断"完整链路。
2. 建立**确定性强、可回归**的五维评分模型，保证同一份简历多次诊断分数一致（支撑"改后对比分数变化"的核心卖点）。
3. 建立**可追溯证据链**，保证每条红色风险都有可定位的原文引用。
4. 建立**可降级**的 LLM 调用链（重试 + 规则引擎兜底），实现零 API Key 也能产出契约合规的完整报告。
5. 提供面向求职者的简历模板与结构化编辑器，实现"不打开 Word 也能写简历并与诊断闭环打通"。

### 5.1 功能需求（源自 SRS）

| 模块 | 核心功能 |

| 简历解析 | 支持 PDF/DOCX/PNG/JPG，OCR 识别扫描件，抽取基本信息、教育、工作、项目、技能、证书、时间线，输出 JSON 并保留原文位置 |

| 支付与订阅 | 免费/按次/月订阅/HR 套餐（MVP 为 Mock） |
| HR 批量 | 上传 JD + 批量简历，输出排序列表、匹配分、风险、简版报告（MVP 串行） |
| 管理后台 | 知识库维护、Prompt 模板版本化、反馈审核、成本监控、公平性检查 |
| 编辑器 | 4 套模板、结构化填写、实时预览、三格式导出、与诊断闭环打通（V1.1 新增） |

### 5.2 非功能需求

性能（单份 ≤60s，批量 100 份 ≤10min）、可用性（99.5%+降级）、安全（HTTPS/加密/权限/审计）、隐私（可删除、默认不用于训练）、公平性（无歧视输出）、可扩展（多模型/多语言/多行业）、成本（单份 API ≤0.5 元）、合规（明确"不构成录用/法律意见"）。

### 5.3 验收标准

- 上传简历 + JD 后 60 秒内生成报告；
- 报告含 ≥5 条可执行改写建议（不足时补真实优点，绝不编造问题）；
- 每条红色风险有原文引用与证据；
- 支付成功后报告可下载；
- 用户可删除数据；
- 公平性检查通过率 100%。

## 六、关键技术问题与技术方案

### 6.1 核心链路设计

```
POST /resumes → 文本抽取 → 规则解析 → 存 raw_text + parsed_json
POST /jds     → 规则解析 → 技能/年限/学历/关键词
POST /tasks   → 202 立即返回 → BackgroundTasks 启动工作流
   └─ 8-Agent 工作流（每步落一行 workflow_steps：status/tokens/cost/latency）
        parse → jd_match → ats → impact → risk → suggestion → report → qc
GET /tasks/{id} → 轮询进度（8 步状态 + 耗时）
GET /reports/{id} → 结构化报告
```

一个关键设计决策：**质检（qc）会剔除或降级发现项，因此引擎在 qc 之后重算一次分数**，避免"总分与问题清单自相矛盾"。

### 6.2 关键技术难点与对策

**难点一：评分必须可回归，不能"同一简历两次分数不同"。**
对策：五维评分（ATS 30% / 影响力 25% / 清晰度 20% / 竞争力差距 15% / 风险 10%）全部由确定性公式 `services/analyze.py` 算出，LLM 不参与打分。这保证了"修改后重新诊断、对比分数变化"的卖点真实可信。

**难点二：证据链不能信任模型输出的位置。**
对策：模型只输出引文，字符区间由 `services/evidence.py` 在原文中重新定位；定位不到的红色风险被质检强制降级为黄色。已验证"每条红色风险都有可定位原文引用"。

**难点三：LLM 调用必须可降级，不能"一挂全挂"。**
对策（三重降级链）：live 调用 DeepSeek → 失败重试（默认 2 次，指数退避）→ 回落该 Agent 的规则引擎实现（标记 `degraded`）；仅 `parse`（critical）失败才终止任务。零 Key 的 mock 模式走的就是规则引擎路径，因此**零 API Key 也能产出契约合规的完整报告**。

**难点四：高质量简历不足 5 条问题时的"诚实"处理。**
对策：`suggestion_agent._ensure_minimum` 先补"简历确实缺失的检查项"，仍不够则补**真实存在的优点**（severity=green，附原文证据 + 面试用法），绝不编造问题。

**难点五：编辑器产出的简历不能与上传简历"分叉"。**
对策：`POST /resumes/from-editor` 把结构化内容渲染成纯文本存入 `raw_text`，使其在 8-Agent 流水线中与上传简历完全等价，无需特殊分支；代价是需保证渲染文本能被 `parse_rules.py` 正确读回（章节用词表说法、日期落行尾、要点以 `- ` 开头），verify 脚本对此有专门断言。

### 6.3 技术栈与 MVP-lite 取舍

| 文档方案 | 本项目实现（MVP-lite） | 升级动作（可回退） |
|---|---|---|
| LangGraph 编排 | `workflow/engine.py` 手写状态机 | 仅替换 engine.py，节点签名已对齐 |
| PostgreSQL + pgvector | SQLite（DDL 同构）+ 侧暴力检索 | 改 DATABASE_URL；embedding 换 Vector(1536)+HNSW |
| Redis + Celery | FastAPI BackgroundTasks + 任务状态表 | launch_workflow 换 Celery task |
| LlamaIndex | 自研切片 + 混合检索 | rag.py 换 LlamaIndex retriever |
| 多模型路由 | DeepSeek 单供应商 + 适配层 | llm.py 加 provider 分支 |
| 登录鉴权 | `X-Device-Id` 匿名隔离 | 替换 get_current_user |
| shadcn/ui | 手写同风格组件（无 Radix） | 按需替换为官方组件 |

**设计铁律**：接口、契约、表结构照文档不动，只换实现层。每项差异都"可回退"——后续升级是"换配置"而非"重写"。

## 七、系统架构与模块设计

### 7.1 总体架构（分层）

```
接入层：Next.js 14（Web） / API
应用层：用户、简历、JD、报告、支付、HR 批量（11 个路由模块）
Agent 编排层：workflow/engine.py 手写状态机
RAG 层：自研切片 + 混合检索（0.6 向量 + 0.4 词面）
数据层：SQLite（DDL 同构 PostgreSQL）/ 文件系统
基础设施：Docker Compose 一键起前后端
```

### 7.2 后端模块

- `app/main.py` 应用入口（异常处理 / CORS / 静态文件 / 启动钩子）
- `app/models.py` ORM，逐表对齐 aaa.md 的 DDL 草案
- `app/agents/` 8 个 Agent（base / parse / jd_match / ats / impact / risk / suggestion / report / qc）
- `services/` 核心服务：`llm`（适配层+降级）、`extract`（抽取+OCR）、`analyze`（五维评分+规则检测）、`evidence`（证据链定位）、`rag`（检索）、`resume_templates`（4 套模板）、`resume_render`（四格式渲染）
- `scripts/` 验证与演示：`verify`（端到端契约验证）、`inspect`（离线报告）、`demo_improve_loop`（改前改后对比）

### 7.3 前端设计

Next.js 14 App Router + TypeScript + Tailwind，视觉统一为"Claude 风格"（暖米白底色、珊瑚色强调、衬线标题、发丝边框）。含首页、编辑器 `/editor`、报告页、定价页、HR 批量页，并提供无头浏览器截图工具用于视觉复核。

### 7.4 数据库设计

严格对齐 aaa.md 的 DDL 草案（users / organizations / resumes / job_descriptions / analysis_tasks / analysis_reports / report_findings / knowledge_docs / knowledge_chunks / workflow_steps / payments / subscriptions / feedbacks / audit_logs）。MVP 用 SQLite 实现同构表结构，表名、列名、字段类型一一对应，便于平滑迁移 PostgreSQL。

## 八、本课题的创新点

1. **确定性强、可回归的评分模型**：五维评分拒绝 LLM 打分，用确定性公式保证"同一简历多次诊断分数一致"，让"改后对比分数变化"这一核心卖点真实可信——这是现有黑箱打分器普遍缺失的。
2. **服务端重新定位的证据链**：不信任模型输出的字符区间，由 `evidence.py` 在原文中重定位引文，定位失败的红色风险强制降级，从机制上杜绝"虚构证据"。
3. **零 Key 可运行的降级架构**：三重降级链使系统在无 API Key 时仍能产出契约合规报告，极大降低演示、测试与冷启动门槛。
4. **"诚实补优点"的建议生成策略**：报告条数不足时不编造问题，而是补真实优点（green），兼顾验收标准与用户信任。
5. **编辑器与诊断闭环单链路融合**：编辑器产物渲染为纯文本进入同一流水线，避免"上传简历"与"编辑器简历"分叉带来的质量不一致。
6. **契约冻结的工程纪律**：API 契约（`api-contract.md`）先行冻结，前后端并行开发，以 170+ 项端到端断言（verify 脚本）防止契约漂移。

## 十一、已知边界与下一步（诚实标注）

MVP 阶段明确未做：真实登录鉴权（用 `X-Device-Id` 匿名隔离，可被伪造）、真实支付验签（pay_url 为 Mock）、HR 批量串行（不校验配额）、OCR 依赖本机 tesseract、多栏排版可能错位、embedding 为本地哈希向量（非语义向量）、mock 模式关键词匹配不做同义归并、无 Alembic 迁移、PDF 导出需配置 LibreOffice、上传简历导出有损。

建议下一步顺序：① 用真实 Prompt 跑 10 份真实简历 + JD 人工评估质量；② 接入真实认证与支付验签；③ 换 PostgreSQL + pgvector 并升级真实语义向量（检索质量提升最大）；④ 引入 Redis + Celery 并发化 HR 批量；⑤ 接 Langfuse 做 LLM 可观测。
