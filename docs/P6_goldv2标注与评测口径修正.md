# P6｜gold v2 标注与检索评测口径修正（2026-10-22）

> 上一轮（P5）结论是"检索算法已不是瓶颈，问题在评测集"。
> 本轮**把评测集修了**，并因此推翻了 P5 的一部分判断 —— 同时也给出了更可信的检索结论。

---

## 1. 做了什么：gold v2（从「结论」推出「依据」）

### 1.1 v1 的两个缺陷

| 缺陷 | 后果 |
|---|---|
| gold 只覆盖 **5 篇自撰文档** | 8 篇外部权威语料（O*NET / McMaster / Dartmouth / SocialTalent / EEOC）**完全不计分**；把 O*NET 排到第 1 也不加分 |
| gold 与"该简历实际有什么问题"**脱节** | 不管缺 Kubernetes 还是缺量化，gold 都是同一组切片 → recall 变成"能否召回固定三篇" |

### 1.2 v2 的做法

`backend/scripts/gold_v2.py` 实现**两级可审计映射**：

```
规则层结论（topic）  →  知识库切片（doc_title, chunk_index, why）
```

例：

```
结论：kw:Kubernetes
  ← 后端工程师能力模型与量化标准 #0
     理由：工程素养层要求「容器化部署」，说明该能力在岗位能力模型里的位置
  ← ATS 关键词匹配的实际工作方式 #1
     理由：要求「中英文技术名词同时出现一次（Kubernetes（K8s））」
  ← Dartmouth 大学：理解申请人追踪系统（ATS）的官方建议 #1
     理由：「关键词要与岗位描述一致」是 ATS 匹配的官方建议
结论：kw:开源
  （知识库中无对应依据 → gold 留空，不凑数）
```

**为什么可审计**：
- 每条映射带 `why`，可人工复核"这切片真的支撑这结论吗"；
- topic 来自**规则层实际输出**（`analyze.rule_baseline_findings`），不是拍脑袋；
- 映射表是纯数据，改一条不影响代码。

**为什么"开源"留空**：知识库里确实没有讲开源贡献的文档。显式留空而不是随便找一篇凑数 ——
这也是 recall 无法到 100% 的真实原因之一。

### 1.3 结果：gold 从 3–4 片扩到 **8–9 片**

| | v1 | v2 |
|---|---|---|
| 每例 gold 切片数 | 3–4 | **8–9** |
| 覆盖文档 | 5 篇（自撰） | **9 篇**（含 O*NET / McMaster / Dartmouth） |
| 依据与结论的关系 | 无（固定列表） | 逐条推导 + 理由 |

## 2. 最重要的发现：v1 的 89.2% 是**假象**

| gold 口径 | 基线 recall@5 |
|---|---|
| **v1**（固定 5 篇自撰规范） | **89.2%** |
| **v2**（从结论推出依据，含外部语料） | **35.4%** |

**同一套检索器、同一批 query，换个 gold 口径，分数从 89.2% 掉到 35.4%。**

这不是检索器变差了，而是 **v1 的 gold 太小太窄**：3–4 片，且都集中在检索器本来就擅长命中的
那两篇文档上。v1 的 89.2% 实际在测"能不能召回固定三篇"，不是"能不能引到点子上"。

> **这条修正了 P5 的判断。** P5 说"89.2% 已接近上限"——在 v1 口径下这句话成立，
> 但 v1 本身是失真的。v2 口径下 35.4% 才是真实起点。

## 3. 第二个发现：`top_k=5` 时**天花板只有 58.8%**

v2 的 gold 平均 **8.5 片**，而 `top_k=5` 最多只能命中 5 片：

```
理论上限 = 5 / 8.5 = 58.8%
实测      = 35.4%
达成率    = 60.2%
```

**这意味着 `top_k=5` 下任何优化都测不出来** —— 天花板压得太低，效应量被结构性上限吃掉。
这正是 P5 里"所有臂都无效"的部分原因（另一部分原因确实是 v1 gold 失真）。

| top_k | 覆盖率（43 切片） | 理论上限（gold 8.5 片） |
|---|---|---|
| 5 | 11.6% | **58.8%** |
| 6 | 14.0% | 70.6% |
| 8 | 18.6% | 94.1% |
| **10** | 23.3% | **100%** |
| 12 | 27.9% | 100% |

## 4. 第三个发现：k=10 时 `persp_only` **稳定双赢**

扫 k=5/6/8/10/12 五个值，只有 **`top_k=10`** 时出现唯一一个在两个口径下都提升的臂：

| 臂 | v1 (Δ) | v2 (Δ) | 判定 |
|---|---|---|---|
| bm25_0.5 | 89.2% (+0.0%) | 35.4%→41.0% (+0.0%) | ＝ 无效 |
| bm25_0.7 | 89.2% (+0.0%) | 41.0% (+0.0%) | ＝ 无效 |
| **mmr_0.7** | 89.2% (+0.0%) | **47.2% (+6.2%)** | ✅ 仅 v2 有效 |
| bm25+mmr | 89.2% (+0.0%) | 35.4% (−5.5%) | ❌ 有害 |
| multi_persp | 92.5% (+3.3%) | 41.0% (+0.0%) | ✅ 仅 v1 有效 |
| **persp_only** | **92.5% (+3.3%)** | **47.2% (+6.2%)** | ✅✅ **双赢** |

### 4.1 但必须说清楚：这个收益很小且不稳定

| top_k | persp_only v1 | persp_only v2 |
|---|---|---|
| 5 | 61.7% (−27.5%) ❌ | 23.6% (−11.8%) ❌ |
| 6 | 55.0% (−34.2%) ❌ | 21.1% (−14.3%) ❌ |
| 8 | 61.7% (−27.5%) ❌ | 35.4% (+0.0%) ＝ |
| **10** | **92.5% (+3.3%)** ✅ | **47.2% (+6.2%)** ✅ |
| 12 | 92.5% (+3.3%) ✅ | 47.2% (−5.6%) ❌ |

**只有 k=10 这一个点双赢，k=12 就又掉回去了。** 这说明它不是一个稳健的改进，
更像是"在特定 k 下碰巧对齐"。

### 4.2 为什么 persp_only 在小 k 下会崩

`persp_only` 是**只用 4 条视角 query**（能力模型 / 量化表达 / ATS 机制 / 合规）做 RRF 融合。
它**不含 JD 宽 query**，所以在 k 小时：

- 每条视角 query 各取前 `max(k, 3)` 条，RRF 后 4 个视角的头名同分；
- 但 **JD 里的具体技能词（Java / Spring / MySQL）没被任何视角 query 覆盖** →
  小 k 下这些 gold 被挤掉；
- k 变大（10）时，各视角能带进来更多条目，JD 技能类 gold 也进来了，才追平并反超。

**这解释了一个反直觉现象**：`multi_persp`（宽 query + 4 视角）在 k=5/8 时与基线持平、
k=10 时 +3.3%、k=12 时归零 —— 融合把宽 query 的优势稀释了。

## 5. 结论

### 5.1 对检索算法的判断（修正 P5）

| P5 的说法 | 本轮的修正 |
|---|---|
| "89.2% 已接近上限" | **在 v1 口径下成立，但 v1 失真**；v2 口径下真实起点是 35.4% |
| "检索算法已不是瓶颈" | **部分正确**：`top_k=5` 下天花板只有 58.8%，确实测不出优化 |
| "所有臂都无效" | **在 v1 + k=5 下成立**；换成 v2 + k=10，`persp_only` 双赢 +3.3/+6.2pp |

### 5.2 真实可用的结论

1. **评测口径比算法更重要**：同一检索器，换 gold 口径分数从 89.2% → 35.4%。
   任何检索改动的评估都必须先确认 gold 与 `top_k` 是否给足了测试空间。
2. **`top_k=5` 是评测的隐形天花板**：v2 gold 平均 8.5 片，k=5 上限 58.8%。
   要测优化，**必须用 k≥8**（上限 94.1%）。
3. **`persp_only` 在 k=10 下双赢，但不稳健**（k=12 失效）。
   → **不建议作为默认路径**，但可以作为"当 top_k 较大时"的可选方案。
4. **`MMR` 在 v2 下 +6.2pp**（k=8/10），但 k=12 转负。
   → 同样不稳健。

### 5.3 为什么仍然不改默认路径

生产链路的 `rag_top_k=5`（`config.py:159`），在这个 k 下：
- 所有臂都无效或有害（见 §4.1 表格 k=5 行）；
- 改 `top_k` 会直接影响 prompt 长度、token 成本、报告条数上限 —— 是产品决策，不是检索优化。

**所以结论是：检索器不改，但要改评测口径（已改）+ 记录"k=10 时的可选方案"。**

### 方法论沉淀（四轮检索优化的完整教训）

| 轮次 | 尝试 | 结果 | 教训 |
|---|---|---|---|
| 1 | scope 融合（每 scope 保底） | 89.2% → 58.3% | 强制覆盖挤掉同文档的第二个 gold |
| 2 | 提示词"query 写宽" | 55% → 41.7% | 指标噪声（σ=0.11–0.29）远大于效应 |
| 3 | BM25 / MMR / 多视角（k=5） | 全部无提升 | **瓶颈在评测集** |
| 4 | 修 gold（v2）+ 扫 k | v1 89.2% 是假象；v2 真实 35.4%；k=5 上限仅 58.8% | **先确认"测试有没有空间"，再优化** |

**四轮里三轮都在错误的层上优化（算法），真正的两个瓶颈是：gold 口径失真、top_k 天花板。**
