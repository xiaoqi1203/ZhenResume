### 为什么选这些来源

1. **O\*NET 是美国政府公开数据（public domain）**，岗位任务是官方采集的，
   比任何"简历攻略"更适合做能力模型的依据；
2. **大学就业中心**是教育机构公开资料，给出的公式与对照例可直接引用；
3. **EEOC** 是执法机构，其"受保护特征 + 差别影响"框架是 AI 筛选工具的合规底线；
4. **SocialTalent** 是招聘行业培训机构，提供解析机制的工程解释。

### 刻意排除的来源

- 简历代写公司/营销号（有商业动机，标准不可信）；
- 无法抓取正文的页面（如 EEOC 官网对自动化抓取返回 403 —— 该条目依据其公开政策框架整理，
  `source_url` 保留供人工复核，并在正文末尾注明）。

## 4. 扩库顺带发现的两个真实缺陷（已修）

### 4.1 数字护栏有覆盖漏洞（编造率 0% → 7.1% → 0%）

第一版护栏只加在 `workflow/agent_nodes._to_findings`（agent 线的分析节点）。
扩库后 `suggestion_agent` 走的是 `finding_utils.coerce_findings`，**绕过了护栏**，
于是又出现编造数字：

```
简历里没有 75 → 改写句写出「P99 降 75%」
```

修法：护栏下沉到 `coerce_findings`（所有 finding 的必经之路），
`agent_nodes` 保留薄别名。修后编造率回到 **0.0%**。

### 4.2 引用在 suggestion 环节被静默丢弃

扩库后实测：分析阶段产出 **17/19 条带引用**，最终报告只剩 **5 条**。
根因：`_select_final` 按严重度截断到 `MAX_FINAL=8`，把带引用的 LLM 条目挤掉了。

修法：截断时**带 `citations` 的条目优先**。修后同一批数据最终引用覆盖率
从 38.5% → **77.3%**（3 例），最好一例 8/8 全带引用。

> 这两个缺陷都是**扩库暴露出来的**，不是扩库引入的 —— 库小的时候条目少、撞不上截断。

## 5. 一个重要结论：scope 融合方案在大库上更差

扩库后重跑 `eval_retrieval`：

| 口径 | 16 切片时 | **43 切片时** |
|---|---|---|
| 单 query 全局排序（现状） | 89.2% | **89.2%** |
| scope 融合 RRF | 58.3% | **30.8%** ❌ |
| 融合 + 每 scope 保底 1 席 | 58.3% | **30.8%** ❌ |

**库越大，强制多维度覆盖的伤害越大**——因为每个 scope 只取 1–2 名参与融合，
而 gold 集中在 `role` 与 `resume_template` 两类，强制给 `industry`/`compliance` 留席位
等于按比例丢弃相关结果。

这进一步确认了上一轮的判断：**`search_scoped` 不合入默认路径**，
保留为"已评测、暂不启用"的方案（代码与注释都在，`scope_quota` 默认 0）。
