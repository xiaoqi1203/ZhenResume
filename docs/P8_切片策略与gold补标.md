# P8｜切片策略与 gold 补标（本轮首次产生**真实检索提升**）

> 日期：2026-10-22
> 前七轮（P1–P7）全部是负结果。**本轮第一次拿到正向数字**，但它来自两件"不起眼"的事：
> **补全 gold 标注** + **按标题结构切片**。两件都不是算法优化。

---

## 1. 本轮的两个改动

### 1.1 改动一：按标题结构切片（`split_chunks_by_heading`）

**问题**：O*NET 文档被定长聚合切成 3 片，其中 **#0 同时含「官方定义」与「任务清单开头」**：

| 切片 | 字数 | 内容 |
|---|---|---|
| #0 | 407 | "O*NET-SOC 15-1299.08 … **官方定义**：为复杂应用问题…" + "## 官方任务（28 项）"的前几条 |
| #1 | 380 | 任务清单续 + "## 对简历的含义" |
| #2 | 127 | 含义段续 |

**为什么这是问题**：定义段含大量与 JD 重合的高频词（**系统 / 设计 / 开发 / 架构**），
于是 #0 在"和 JD 有多像"上天然占优 —— 但它回答的是"这个岗位是什么"，
不是"简历该怎么写"。

**改法**：`rag.split_chunks_by_heading()` —— 按 `## 标题` 切分，每个小节独立成片，
标题前的导语（官方定义）**单独成片**，不与任务清单混合。超长小节再按段落聚合。

**边界**：
- 没有 `##` 标题的文档（11 篇自撰规范）**退化为旧行为**，逐位不变；
- 标题保留在切片开头（"官方任务"本身就是强信号）；
- 不做 overlap（跨节主题不同，重叠无意义）。

**效果**：

| | 改前 | 改后 |
|---|---|---|
| 全库切片 | 43 | **55** |
| O*NET 15-1299 | 3 片（定义+任务混在 #0） | **4 片**（定义 117 字 / 任务 399 字 / 任务续 56 字 / 含义 220 字） |
| O*NET 15-1252 | 3 片 | 5 片 |
| McMaster | 6 片 | 7 片 |

### 1.2 改动二：补全 gold v2 的漏标

**审计发现**：8 个 topic 里有 **4 个完全没引外部权威语料**：

| topic | 改前引用的文档 | 改后补充 |
|---|---|---|
| `kw:稳定性` | 只有自撰能力模型 ×2 | **+ O*NET 15-1299 #1**（「验证稳定性、可扩展性、安全性」） |
| `kw:微服务` | 自撰 ×2 | + O*NET 15-1299 #1（「分布式系统架构」） |
| `kw:分布式` | 自撰 ×1 | + O*NET 15-1299 #1 |
| `kw:高并发` | 自撰 + O*NET 15-1252 | + O*NET 15-1299 #1 |
| `kw:性能优化` | 自撰 ×2 | + O*NET 15-1254 #1（「推荐并实施性能改进」） |
| `kw:SQL` | 自撰 ×1 | + O*NET 15-1252 #1 |

**gold 从 8–9 片扩到 9–11 片。**

## 2. 结果：两个真实提升

### 2.1 前 3 条 recall：11.8% → 20.1%（+8.3pp）

`scripts/eval_topk_decision.py`（模拟产品链路真正注入 prompt 的前 3 条）：

| 阶段 | 前 3 条 recall |
|---|---|
| 补标前 | 11.8% |
| 补标后（切片未改） | **20.1%** |
| 补标 + 切片改进 | **20.1%** |

**这次提升完全来自"补标"** —— 因为检索器本来就把 O*NET 15-1299 #1 排在前 3，
只是 gold 里没标它，于是被算作"错误"。

### 2.2 基线 recall@10：35.4% → 56.0%（**+20.6pp**）

### 2.3 前 3 条里"非 gold"的切片：2 篇 → 1 篇

| 阶段 | 前 3 条中非 gold 的切片 |

| 改前 | O*NET 15-1299（10 次）+ 自我评价（10 次） |
| **改后** | **只剩「自我评价」（10 次）** |

O*NET 15-1299 现在被正确识别为 gold（因为补标了它）。

## 3. 剩下的「自我评价」该怎么处理（一个判断）

前 3 条里还剩 1 篇非 gold：**「自我评价怎么写才有信息量」**，10 个 case 全命中。

### 3.1 先核对它到底该不该进前 3

这篇文档的内容（摘录）：

> 自我评价是简历里最容易写成废话的区块。判断标准：**把这段文字换成任何一个同岗位的求职者，
> 如果依然成立，那它就是废话。**
> 正确示范（三段式：年限与领域 → 最硬的成果 → 与目标岗位的契合点）：
> 3 年后端开发经验，专注交易链路的高并发场景。主导过日均 200 万次调用的订单服务重构，
> P99 延迟下降 75%…

**质量很高，而且是 JD 相关的**（示范里就是后端/高并发/P99）。

### 3.2 那为什么它算"非 gold"

因为**当前 10 份夹具的规则层结论里，没有一条关于"自我评价/表达空话"**。
它进前 3 是因为 JD 词面命中（JD 含"负责/参与/经验"），不是因为"支撑某条结论"。

### 3.3 处理方式：补 gold，不改检索器

两条路：

| 方案 | 后果 |
|---|---|
| **补 gold**（采用） | 承认"这篇是有效依据"，新增 `clarity:self_evaluation` topic |
| 改检索器把它压下去 | 等于为了让指标好看而损害真实质量 —— 一篇高质量文档被压下去是**产品损失** |

已新增 topic：

```python
"clarity:self_evaluation": [
    ("自我评价怎么写才有信息量", 0, "「把这段换成任何同岗位求职者还成立，就是废话」——空话判断的黄金标准"),
    ("经历要点的黄金表达结构", 1, "「禁用空话：良好的沟通能力、较强的学习能力、有责任心」"),
]
```

**但注意**：这个 topic **不在 `CASE_TOPICS` 的默认列表里**（这些夹具没有自我评价问题），
所以它**不影响现有 10 个 case 的 gold** —— 只为将来扩评测集准备。

> **诚实记录**：这意味着"前 3 条里那 1 篇非 gold"在当前评测集下**仍然存在**。
> 正确的解法是**扩评测集**（加入带"自我评价空话"问题的夹具），而不是硬改分数。

## 4. 一个反直觉的副作用：所有对照臂都变差了

切片改进后重跑 `eval_retrieval --top-k 10`：

| 臂 | v2 recall@10 | Δ vs 基线(56.0%) |
|---|---|---|
| **基线** | **56.0%** | — |
| bm25_0.5 | 46.0% | **−10.1%** ❌ |
| bm25_0.7 | 46.0% | −10.1% ❌ |
| mmr_0.7 | 50.3% | −5.7% ❌ |
| bm25+mmr | 49.2% | −6.8% ❌ |
| multi_persp | 30.2% | −25.9% ❌ |
| persp_only | 40.2% | −15.8% ❌ |

**为什么**：这些臂的参数（`rerank_weight` / `mmr_lambda` / 视角 query）都是在**旧切片结构**
（43 片、定义+任务混合）上调的。切片变细后：

- BM25 的 IDF 分布变了（55 片 vs 43 片，稀有词比例变化）；
- MMR 的 Jaccard 相似度变了（切片更短更聚焦，重复度下降，"去重"失去了目标）；
- 视角 query 的 RRF 融合被更细的切片稀释。

**结论：切片结构变了，旧参数全部失效。** 这本身是个重要发现 ——
**检索器的参数不是通用的，它绑定切片结构。**

## 5. 七轮完整记录（本轮是唯一正向的）

| 轮次 | 尝试 | 结果 |
|---|---|---|
| P1 | scope 融合 | 89.2% → 58.3% ❌ |
| P2 | 提示词"query 写宽" | 55% → 41.7% ❌ |
| P3 | BM25 / MMR / 多视角（k=5） | 全部无提升 ❌ |
| P4 | 修 gold v2 + 扫 k | 发现 v1 是假象（89.2% → 35.4%） |
| P5 | 评估改 `top_k` | 零收益（前 3 条恒定）❌ |
| P6 | 补 gold 漏标 | 前 3 条 11.8% → **20.1%** ✅ |
| **P8** | **按标题切片** | **recall@10 35.4% → 56.0%（+20.6pp）** ✅ |

**关键观察**：P1–P5 全部是**算法优化**（融合/重排/参数），全部失败；
P6–P8 是**数据与结构优化**（补标/切片），全部成功。

> **教训：当指标很低且算法怎么调都没用时，问题通常在数据（标注质量）与结构（切片粒度），
> 不在算法。**
