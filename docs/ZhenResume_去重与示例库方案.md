# 去重 · 统计范式 · 范文库 · 人才库 —— 方案（v2）

> 状态：**方案，待拍板**。v2 相比 v1 的最大变化：**删掉"把 HR 简历匿名化后入示例库"这条路线**，
> 改为"HR 数据只出聚合统计；范文走求职者授权；示例走合成"。
>
> v1 为什么被否：`2021-2023 在 A 公司做订单系统，接口 P99 从 800ms 降到 120ms` 这种"去掉姓名"的记录，
> 其准标识符组合的唯一性 k≈1 —— 属于典型 **singling out（唯一识别）**，仍是个人信息，
> 且 HR 对其只有"招聘目的"的处理权，无权授权给你做范文。

---

## 0. 一句话模型：三个数据源，五条产出通道

| 数据源 | 产出 | 是否落原文 | 需要什么授权 | 解决什么问题 |
|---|---|---|---|---|
| **HR 批量导入** | ① **聚合统计范式**（不落原文）<br>② **筛选行为信号**（谁被通过/淘汰） | ❌ 不落 | 不需要逐个同意（聚合到 k≥10 后非个人信息） | "同岗位该怎么写" + 校准评分算法 |
| **求职者（一键授权）** | ③ **范文原文**（脱敏后） | ✅ 落（本人授权） | 一键勾选 + 可撤回 | "看一份真实的高分简历" |
| **合成（照统计生成）** | ④ **示例句** | ✅ 落（但不对应任何真人） | 不需要 | "改完长什么样"（范式的可视化） |
| HR 导入的候选人 | ⑤ **认领邀请**（触达） | ❌ | 候选人认领后该份数据才可用 | 人才库的合法增长 |

**核心原则：识别力来自"组合的唯一性"，不是姓名。** 所以策略不是删掉细节，而是把"时间 × 公司 × 业务域 × 量级"这四个维度**打散**，不让它们同时精确出现。

**定位一句话**：HR 侧是**需求侧 + 获客渠道 + 标注数据**；候选人本人是**数据来源**。

## 1. #3① 批量去重（零风险，先做）

### 1.1 三级判定

| 级别 | 判据 | 解决什么 | 成本 |
|---|---|---|---|
| L1 文件级 | 原始文件 `sha256` | 同一份 PDF 重复上传（HR 最常见） | 极低 |
| L2 内容级 | 归一化文本 `sha256`（去空白/标点/换行、全角转半角、去页眉页脚） | 同一简历导成 PDF 和 DOCX 各传一次 | 低 |
| L3 语义级 | 向量相似度 > 0.98 | 换文件名、微调一两处 | 中（需 pgvector，最后做） |

### 1.2 关键设计：**去重 ≠ 静默丢弃**

HR 场景下"重复投递"本身是信号，必须可见：

- 保留批次条目，但**复用已有 `resume_id`**，标 `duplicate_of` / `dedup_level`
- 该简历 **7 天内有报告** → 直接复用报告（省钱），标 `report_reused = true`
- 报告更旧 → 重跑（"再次投递时内容变了"也是风险信号）
- **排序表上显式标注**，不隐藏

### 1.3 数据模型

```sql
ALTER TABLE resumes ADD COLUMN file_sha256    char(64);
ALTER TABLE resumes ADD COLUMN content_sha256 char(64);
ALTER TABLE resumes ADD COLUMN duplicate_of    uuid REFERENCES resumes(id) ON DELETE SET NULL;
CREATE INDEX idx_resumes_file_sha    ON resumes (file_sha256)    WHERE file_sha256 IS NOT NULL;
CREATE INDEX idx_resumes_content_sha ON resumes (content_sha256) WHERE content_sha256 IS NOT NULL;
```
> **不加全局唯一约束**：同一文件被不同用户各传一份是两份数据，多租户下不能互相可见；
> 唯一性只在"同一 user + 同一 hash"范围内判定。

### 1.4 落地

- 新增 `services/dedup.py`：`compute_hashes(text)` / `find_duplicate(db, user_id, ...)`
- 上传接口与批量创建接口在建 `AnalysisTask` **之前**查重（否则钱已经花了）

### 1.5 收益

100 份里 15 份重复 → 省 15 × ¥0.0213 ≈ **¥0.32/批** + **排名不被污染** + 多一个风险维度。

**工作量：0.5 天。**

## 2. #3② HR 聚合统计范式（**现在就能做，不碰个人数据 —— 建议紧跟去重做**）

### 2.1 为什么这项最被低估

1. **不碰个人数据** → 没有合规争议，现在就能上
2. **吃到 HR 数据最大的优势**：量大、**新鲜**（"2026 Q1 后端岗"比"两年前的范文"有用）
3. **两个消费者，内部那个更值钱**：
   - ① **内部**：自动生成/校准知识库里的「岗位能力模型」（现在是你**手写的 11 篇**）→ 诊断更准
   - ② **外部**：诊断报告新增"同岗位对标"栏 → 立刻可见的产品提升

### 2.2 聚合口径（第一版就这些，别贪多）

按 `(role_family, period)` 分格，每格统计：

| 指标 | 定义 | 用它给出什么建议 |
|---|---|---|
| `sample_size` | 该格样本数 | 合规闸门 + 展示（"基于 428 份"） |
| `score_p75` | overall_score 的 75 分位（"高分线"） | 定义什么叫"高分简历" |
| `highlight_avg_chars` | 经历要点平均字数 | "你 68 字，高分 42 字" |
| `quantified_per_project` | 每个项目的量化数字个数 | "你 1.2 个，高分 2.1 个" |
| `action_verb_variety` | 动词去重数量 | "你 6 种，高分 11 种" |
| `jd_keyword_coverage` | 命中 JD 关键词比例 | "你 61%，高分 78%" |
| `star_completeness` | 规则层 STAR 结构完整度 | 结构建议 |
| `top_missing_keywords` | 该格最常缺的 JD 关键词 top10 | 告诉求职者该补什么 |
| `top_skills` | 简历里出现频率 top20 技能 | 技能画像 |
| `pd_trend` | 与上一周期的差值 | 行业趋势（**可售卖的报告内容**） |

**role_family 怎么来**：从 `parsed_jd` 的 title + 关键词映射到岗位族（后端/算法/前端/产品/运营/数据/测试…），
映射表放配置里可人工改。

### 2.3 ⚠️ 聚合闸门（这一条既是工程细节，也是法律论证的前提）

```sql
-- 只输出样本量足够的格子
WHERE sample_size >= 10
```

**为什么必须有**：某格只有 1 条时（"某公司那年唯一做订单系统的后端"），聚合结果能反推出那个人 ——
又变回个人信息了。**k≥10 是"这条路合法"的前提，不是优化项。**

报告里也要**明示样本量**（"基于同岗位 428 份高分简历"），既合规又建立信任。

### 2.4 数据模型

```sql
CREATE TABLE role_stats (
  id            uuid PRIMARY KEY,
  role_family   varchar(64) NOT NULL,
  period        varchar(8)  NOT NULL,        -- '2026-Q1'
  sample_size   int         NOT NULL,
  score_p75     int,
  metrics       jsonb       NOT NULL,        -- 上面那批指标
  generated_at  timestamptz NOT NULL,
  UNIQUE (role_family, period)
);
CREATE INDEX idx_role_stats_pick ON role_stats (role_family, period DESC);
```

### 2.5 怎么算：**批次完成后离线聚合，不要实时算**

```
HR 批次完成（或每小时/每天定时）
        ↓
scripts/aggregate_stats.py --period 2026-Q1
        ↓
按 (role_family, period) 扫描已完成的报告 → 算指标 → upsert 进 role_stats
        ↓
闸门：sample_size < 10 的格子不出数
```

**注意**：聚合只读 `analysis_reports`（分数/发现项）+ `parsed_jd`（岗位族），
**不把 `resumes.raw_text` 写进任何统计表** —— 中间过程在内存里算完就丢。

### 2.6 两个消费者怎么接

**① 喂给知识库（内部，收益更大）**

现在知识库是 11 篇手写文档（`services/seed.py`）。新增一条数据通路：

```
role_stats  →  生成「岗位能力模型」文档（自动）
            →  写入 knowledge_docs（scope='role_model', source='auto_stats'）
            →  检索时被 jd_match / ats 节点引用
```

能力模型从"手写经验值"变成"真实数据算出来的"，**诊断准确度直接提升**，且不用你维护。

**② 进诊断报告（外部，立刻可见）**

```
【同岗位对标】基于同岗位 428 份高分简历（后端 · 2026 Q1）
  · 要点平均字数     你 68 字  →  高分 42 字   ⚠️ 长 62%，建议压到 40 字内
  · 每个项目量化数字  你 1.2 个 →  高分 2.1 个
  · JD 关键词覆盖     你 61%   →  高分 78%     ⚠️ 缺 Java、Spring Cloud
  ─────────────────────────────────────────────
  示例（合成，非真实简历）：
  "负责订单主链路性能治理，通过索引重构与缓存分层，将下单接口 P99 从 800ms 降至 120ms"
```

**先给数字对比（可执行），再给示例（可模仿）。** 只有数字太抽象，只有示例太主观 —— 配对才有效。

**工作量：1.5 天**（聚合脚本 + 报告字段 + 契约更新）。

## 3. #3③ 候选人认领机制（**人才库的正解**）

### 3.1 为什么必须有它

HR 导入的简历**不能**成为你的人才库资产（归属 + 目的外使用）。唯一合法路径是**让候选人自己认领并授权**：

```
HR 导入候选人简历
      ↓
平台用「手机号/邮箱的哈希」识别出这份简历的主人（⚠️ 只存哈希，不存明文）
      ↓
通过 HR 侧合规转发 / 系统邮件邀请：
   "你被「某后端岗」关注，认领后可查看匹配度并加入人才库"
      ↓
候选人点击认领 → 验证手机 → 同意授权
      ↓
✅ 这份数据现在归用户自己 → 可合法进人才库、可被推荐给其他 HR、可随时撤回
```

### 3.2 关键设计

| 点 | 做法 |
|---|---|
| 身份匹配 | 只存 `phone_hash` / `email_hash`（加盐 SHA256），**不存明文** —— 否则你自己成了"身份映射表"这个新风险源 |
| 授权书要点 | 用途（人才库/推荐给其他 HR）、范围、期限、**可撤回**、撤回后 15 日内硬删 |
| 双赢话术 | 候选人想知道"我为什么没被选中"（真实痛点）；HR 得到更多可匹配人才 |
| 核心指标 | **认领率 = 认领数 / 邀请数**。20% 就是很好的数字，且是**零获客成本** |
| 数据可携带 | 候选人可导出/删除自己的档案 |

**工作量：2–3 天**（需前置：通知渠道 + 授权页 + 手机验证）。

## 4. #3④ 求职者授权范文库

### 4.1 触发

```
报告完成
  → overall_score >= EXEMPLAR_MIN_SCORE（建议 85）
  → 用户已勾选授权
  → 通过去识别闸门
  → 入库（status='active'）
```
评分用**规则层 overall_score**（确定性），保证"这份简历能不能入库"可复现。

### 4.2 ⚠️ 去识别闸门（三种攻击一起测）

| 测试 | 问法 | 不通过就 |
|---|---|---|
| **singling out** | 给同行业的人看，他能猜出是谁吗？ | 继续泛化 |
| **k 值** | 按"行业层级 × 岗位族 × 时间段精度 × 业务域"分格，**每格 ≥10 条** | 降低精度（年份 → "N 年经验"） |
| **linkage** | 额外给一条外部信息（"他在这家公司"），能唯一确定吗？ | 打断该组合 |

**泛化规则**（`services/anonymize.py`）：

| 保留（有价值） | 泛化/抑制（去识别） |
|---|---|
| 岗位族、技能、技术栈 | 具体公司名 → 删除或"某互联网公司" |
| 经历的结构（STAR、量化密度） | 精确起止月 → 年 或 "N 年经验" |
| 量化成果的**类型**（性能/成本/效率） | **具体业务域** → "核心业务链路" |
| 动词与句式 | 学校名 → "某 211 院校"；团队规模 → 泛化 |

### 4.3 维护四把刀

| 顺序 | 规则 |
|---|---|
| ① 撤回优先 | 取消授权 → **立刻硬删**（清空正文） |
| ② 容量上限 | 每岗位族 **200 条**，超出按 `(score DESC, use_count DESC, created_at DESC)` 淘汰末尾 |
| ③ 时效 TTL | **12 个月**下架（写法与热词逐年变） |
| ④ 质量淘汰 | 90 天零使用且该族已满 → 清掉 |

```sql
WITH ranked AS (
  SELECT id, row_number() OVER (ORDER BY score DESC, use_count DESC, created_at DESC) AS rn
  FROM exemplars WHERE role_family = :rf AND status = 'active'
)
UPDATE exemplars SET status='removed', removed_reason='capacity'
WHERE id IN (SELECT id FROM ranked WHERE rn > 200);
```

**工作量：1.5 天**（依赖前端授权勾选框，等风格定型）。

## 5. #3⑤ 合成示例（"范文的可视化"，零识别风险）

### 5.1 为什么用合成而不是脱敏

脱敏真简历一泛化就空洞，而"空洞"恰恰是低分简历的特征。合成可以**既具体又不对应真人**：

> "2021-2023 在某电商平台负责订单主链路，通过索引重构与缓存分层，把下单接口 P99 从 800ms 降到 120ms"

公司、系统、数字全部照统计分布生成 → 读起来和高分简历一样具体，但**不指向任何真实个人**。

### 5.2 生成流程与质量闸门

```
role_stats（某岗位族的统计范式）
      ↓ LLM 生成 3–5 条示例（明确要求：公司/系统/数字虚构，写法照范式）
      ↓ 闸门① 与所有源简历的向量相似度 < 0.85（防止模型复述原文）
      ↓ 闸门② 人工抽检（首批）
      ↓ 入库（synthetic_examples，source='synthetic'）
```

**工作量：1 天**（需 ② 先有数据）。

## 6. 合规红线汇总（一句话版）

| 数据 | 能做 | 不能做 |
|---|---|---|
| HR 导入的候选人简历 | 参与**聚合统计**（k≥10）、作为**认领邀请**的触达对象、贡献**筛选行为信号** | ❌ 入范文库 ❌ 入人才库 ❌ 推荐给其他 HR ❌ 脱敏后当范文 |
| 求职者自己的简历 | 有授权 → 脱敏入范文库 | ❌ 未经授权入库 |
| 合成示例 | 自由使用 | ❌ 与源简历相似度过高（>0.85） |

**三条自检**：singling out / k≥10 / linkage —— 任一不通过就不入库。

> 声明：非法律意见。商业化前建议法务确认两件事：
> ① HR 数据做聚合统计是否构成目的外使用（核心争点是聚合粒度）；
> ② 认领授权书的条款措辞。

## 9. 与报告的对应关系（契约要改的地方）

诊断报告新增一节（`api-contract.md` §5 加子节）：

```json
{
  "benchmark": {
    "role_family": "后端",
    "period": "2026-Q1",
    "sample_size": 428,
    "metrics": [
      {"key": "highlight_avg_chars", "mine": 68, "peer": 42, "verdict": "worse", "hint": "压到 40 字内"},
      {"key": "quantified_per_project", "mine": 1.2, "peer": 2.1, "verdict": "worse"},
      {"key": "jd_keyword_coverage", "mine": 0.61, "peer": 0.78, "verdict": "worse",
       "missing": ["Java", "Spring Cloud"]}
    ],
    "examples": [
      {"text": "……", "source": "synthetic"}
    ]
  }
}
```

- `sample_size < 10` 时 `benchmark` 返回 `null`（前端整块隐藏）
- `examples[].source` 只能是 `synthetic`；真实范文需本人授权，走前端另设入口
