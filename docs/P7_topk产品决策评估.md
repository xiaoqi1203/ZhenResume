# P7｜`top_k` 产品决策评估（结论：不该改）

> 日期：2026-10-22　｜　状态：**已评估，结论是不改**
> 上一轮（P6）识别出"`top_k=5` 天花板只有 58.8%"，并建议把 `top_k` 当产品决策评估。
> 本轮评估完，**结论与预期相反：改 `top_k` 对产品零收益。**

---

## 1. 为什么这个评估值得做（先讲清预期）

P6 的推理链是：

```
v2 gold 平均 8.5 片  →  top_k=5 最多命中 5 片  →  上限 58.8%
                    →  提到 top_k=10 理论上限 100%
                    →  "所以应该提 top_k"
```

听起来成立。**但它漏了一个关键事实：产品链路并不把 top-k 全塞进 prompt。**

---

## 2. 关键发现：`top_k` 与 prompt 注入量**完全解耦**

### 2.1 代码事实

| 位置 | 行为 |
|---|---|
| `workflow/nodes.py:70` | `rag.search(top_k=settings.rag_top_k)` → 取回 top_k 条存进 state |
| `agents/base.py:63` | `knowledge_digest(limit=3, max_chars=300)` → **只取前 3 条**拼进 prompt |
| `agents/report_agent.py:52` | `knowledge_hits[:3]` → 报告级引用最多 3 条 |
| `workflow/hr_nodes.py:54` | `knowledge_hits[:3]` |
| `workflow/agent_nodes.py:106` | `knowledge_hits[:3]` → `knowledge_seed` |

**所以 `top_k` 只决定"候选池多大"，而注入 prompt 的永远是前 3 条。**

### 2.2 实测验证

`scripts/eval_topk_decision.py` 模拟 `knowledge_digest` 的真实行为：

| top_k | 前 3 条 recall（v2 gold） | 前 3 条 scope | **prompt 字符** | 返回条数 |
|---|---|---|---|---|
| 3 | 11.8% | 2.00 | **978** | 3.0 |
| 5 | 11.8% | 2.00 | **978** | 5.0 |
| 8 | 11.8% | 2.00 | **978** | 8.0 |
| 10 | 11.8% | 2.00 | **978** | 10.0 |
| 12 | 11.8% | 2.00 | **978** | 12.0 |

**三列数字一个都没变。**

- `prompt 字符` 恒定 978 → **改 top_k 对 token 成本零影响**（成本不是理由，收益也不是）；
- `前 3 条 recall` 恒定 11.8% → **改 top_k 对质量零影响**。

### 2.3 为什么前 3 条不随 top_k 变

因为**排序是确定性的**：`rag.search` 先按混合分降序排好，再截断 `[:top_k]`。
前 3 条永远是分数最高的那 3 条 —— 扩大 `top_k` 只是让第 4 名及以后也返回，
**不会改变前 3 名的身份**。

实测（`rag_A00`）：

| top_k | 前 3 条 | 第 4 名及以后 |
|---|---|---|
| 3 | 后端能力模型(★gold) / O*NET 15-1299 / 自我评价 | （无） |
| 5 | **完全相同** | 表达结构 / 后端能力模型#1 |
| 12 | **完全相同** | 表达结构 / 后端能力模型#1 / O*NET×5 / ATS / 公平性 |

## 3. 顺带查清：前 3 条里真正的问题是什么

前 3 条里固定有 2 条不是 gold，且**在全部 10 个 case 里都是同两篇**：

| 文档 | 出现次数（前 3 条中非 gold） |
|---|---|
| O*NET 15-1299.08 计算机系统工程师/架构师 | **10 次**（每个 case 都有） |
| 自我评价怎么写才有信息量 | **10 次**（每个 case 都有） |

### 3.1 分数拆解（`rag_A00`）

| 文档 | 向量分 | 词面分 | 混合分(0.6v+0.4l) |
|---|---|---|---|
| **后端能力模型（gold）** | 0.600 | 0.409 | **0.523** ← 第 1 |
| **O*NET 15-1299** | 0.462 | 0.305 | **0.399** ← 第 2 |
| **自我评价** | 0.381 | 0.354 | **0.370** ← 第 3 |
| 后端能力模型#1（gold） | 0.362 | 0.268 | 0.324 ← 第 4 |
| O*NET 15-1252 | 0.361 | 0.226 | 0.307 |

**这两篇的分数是"真实"的** —— 它们确实与 JD 宽 query 有词面/语义重叠：

- **O*NET 15-1299（系统架构师）**：JD 写"架构设计""服务治理""容量评估"，该文档讲系统架构任务，
  词面高度重合；
- **自我评价**：JD 宽 query 里含"负责""参与""经验"等词，该文档讲"怎么写自我评价"，
  恰好命中这些高频词。

**这不是 bug，是排序信号的固有局限**：词面/语义相似 ≠ "这条依据能支撑这条结论"。

### 3.2 与 P6 的 gold v2 对照（**此处修正过一版错误结论**）

⚠️ **本节的初版写错了，这里保留修正痕迹**：

> 初版说「O*NET 15-1299 在 v2 gold 里是有映射的（`kw:稳定性` / `kw:高并发` 都引了它），
> 但 gold 引的是 #1/#2 片，而检索排到前 3 的是 #0 片」。

**实测核对后这个说法是错的**：`scripts/gold_v2.py` 的 `TOPIC_CHUNKS` 里，
O*NET 15-1299 **一次都没出现**（`kw:稳定性` 只引了后端能力模型 #0/#1；
`kw:高并发` 引了后端能力模型 #0 + O*NET 15-1252 #1）。

**实际情况是**：

| | 事实 |
|---|---|
| O*NET 15-1299 各片得分 | #0 = 0.307 / **#1 = 0.399（最高）** / #2 = 0.273 |
| 检索排到前 3 的 | **#1**（任务片，含「验证稳定性/可扩展性」「制定系统标准」） |
| 它在 gold 里吗 | **不在** |

也就是说：**检索器把「真正讲任务与标准」的那一片排到了第 2 —— 这个排序是对的；
是我的 gold v2 标注漏掉了它。**

这说明 P6 的 gold v2 仍有漏标：`kw:稳定性` 只标了自撰的能力模型，
而 O*NET 的「验证稳定性、可扩展性、安全性」是更权威的同主题依据，却没被标进去。

**这反而佐证了 P7 的核心结论**：前 3 条的质量问题**不在排序，而在 gold 标注的完整性**。

## 4. 结论

### 4.1 三条明确结论

| # | 结论 | 证据 |
|---|---|---|
| 1 | **不该改 `top_k`** | 前 3 条 recall 与 prompt 字符在 k=3~12 下**完全不变** |
| 2 | **P6 的"k=10 双赢"是评测现象，对产品无意义** | 那个提升来自"top-10 里有没有 gold"，而产品只注入前 3 条 |
| 3 | **真正的瓶颈是"排序选不中正确的那一片"** | 前 3 条里 2 条是"主题对但切片错"（O*NET #0 vs gold #1/#2） |

### 4.2 这修正了 P6 的建议

| P6 的说法 | 本轮的修正 |
|---|---|
| "`top_k` 是当前最大瓶颈，建议提到 8/10" | **错**。top_k 与 prompt 注入量解耦，改了零收益 |
| "k=5 上限 58.8% 压低了效应量" | 在 `recall@k` 口径下成立，但**产品不看 recall@k，只看前 3 条** |
| "k=10 时 persp_only 双赢" | 是评测层面的真实现象，但**不能转化为产品收益** |

### 4.3 真正的下一步（依据 §3.2 的修正）

**先修 gold 标注，再谈切片策略。** 因为 §3.2 证明了：检索器把「任务片」排到第 2 是对的，
是 gold 漏标了它。在 gold 完整之前，任何"排序不准"的判断都不可信。

| 优先级 | 事项 | 理由 |
|---|---|---|
| **P0** | **补全 gold v2 的漏标**（本次已发现 `kw:稳定性` 漏了 O*NET 15-1299 #1） | 依据完整性是评测可信的前提 |
| **P1** | **切片粒度/切分策略**：把「官方定义」与「任务清单」分开切 | 定义段含大量 JD 高频词（系统/设计/开发），会与任务段竞争排名 |
| **P1** | **按结论定制 query**：现在所有结论共用一条 JD 宽 query | Agent 多轮在做这件事，fixed 线没有 |
| **P2** | 注入前去重（同一文档最多 1 片） | 前 3 条已有同文档多片的情况 |
| **P2** | 若以上改完仍不够，再考虑 cross-encoder | 到那时才有明确目标 |
| ❌ 不做 | 改 `top_k` | 实测零收益（本轮核心结论） |

## 6. 五轮检索优化的完整教训

| 轮次 | 尝试 | 结果 | 教训 |
|---|---|---|---|
| 1 | scope 融合 | 89.2% → 58.3% | 强制覆盖挤掉同文档的第二个 gold |
| 2 | 提示词"query 写宽" | 55% → 41.7% | 指标噪声（σ=0.11–0.29）远大于效应 |
| 3 | BM25 / MMR / 多视角（k=5） | 全部无提升 | 瓶颈在评测集 |
| 4 | 修 gold（v2）+ 扫 k | v1 89.2% 是假象；v2 真实 35.4% | 先确认测试有没有空间 |
| 5 | 评估改 `top_k` | **零收益**（前 3 条恒定） | **先确认"改动会不会真的传到用户"** |

**五轮里有四轮都在优化"指标"，而真正的产品链路只看前 3 条。
最后一轮才把"指标 → 产品行为"这条链打通。**

> **最贵的教训：优化一个指标之前，先确认这个指标和用户看到的东西之间有没有因果关系。**
> `recall@k` 与"注入 prompt 的前 3 条"之间，没有因果关系。
