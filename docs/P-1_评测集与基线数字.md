## 1. 为什么用"夹具"而不是人工标注

| 方案 | 问题 |
|---|---|
| 真实用户数据标注 | `data/uploads/` 去重后**只有 9 份唯一文本**，且均为测试夹具（`resume_weak.txt`、`重建后冒烟-技术岗`、`编辑器简历-社招后端`、`空窗期已说明`）——样本量与真实性都不足 |
| 人工逐行标注 | 需要人工判定 100+ 行，成本高、不可复现 |
| **夹具（采用）** | 每份简历的"哪些字面缺失是真差距、哪些是表述差异"**在生成时即已知** → ground truth 可自动计算 |

夹具配方（30 份）：

| kind | 份数 | 含义 | 期望 |
|---|---|---|---|
| `equiv` | 20 | 用**不同的词**表达 JD 要求的能力（如用"多服务调用链路治理"表达"分布式"） | 该关键词判 `false_gap` 且证据可定位 |
| `real` | 3 | 内容与目标能力无关（只有内部后台、官网、工单） | 期望几乎全为 `real_gap` |
| `mixed` | 5 | 同时含若干等价表述与若干真缺失 | 检验精度 |
| `weak` | 2 | 空泛、无量化、无等价表述 | 下限样本 |

**ground truth 必须与规则层对齐**（生成器 post-pass 实现）：只有"规则层确实列为缺失"的关键词才计入 recall 分母。
实测因此剔除了 6 个设计项——`容器化`×4（等价表述里写了 Docker/Kubernetes，已被字面覆盖）、`SQL`×2（`MySQL` 含子串被命中）。

→ 有效假差距 **26 个**（recall 分母）、真差距 **75 个**。

## 2. 基线数字（单次 LLM 调用）

### 2.1 首轮（qwen3.8-max，P0 之前）

```
engine=single  fixtures=30  elapsed=292s  LLM cost=CNY 0.1525  (30 次调用)

假差距 recall（声明子集） = 23/26 = 88.5%
假差距 precision（严格）  = 23/76 = 30.3%   ← 下界，见 §4
证据定位通过率            = 76/76 = 100.0%
真差距误判率（全量判定）  = 0/23  =  0.0%   ← 最可信的指标
ATS 均值：v1 等权 56.1  |  v2 分层 59.4  |  v2 分层+语义 66.1
```

### 2.2 P0 完成后的重算（`eval_cache_20261016-184417.json`）

P0 修好加分项抽取后，JD 要求从 **18 项 → 20 项**（新增 bonus：`稳定性`/`开源`/`云原生`/`Service Mesh`），
分母变化使绝对分数整体下移，因此**上一节的 ATS 绝对值不可与本节直接比较**：

```
假差距 recall（声明子集） = 23/26 = 88.5%     ← 判定质量不受解析改动影响
证据定位通过率            = 76/76 = 100.0%
真差距误判率（全量判定）  = 0/23  =  0.0%
ATS 均值：v1 等权 54.3  |  v2 分层 56.9  |  v2 分层+语义 63.4
```

**三条关键结论（两轮一致）**

1. **`locate_quote` 硬校验 100% 通过**（76/76）——"模型编造引文"这个最大风险，在真实数据上没有触发一次。
2. **真差距误判率 0%**——模型没有把"确实缺失的能力"说成"其实具备"。这是不会冤枉简历的那一侧，最要紧。
3. **语义修正的增益稳定在 +6.5 ~ +8.7 分**（分层另有 +1.8 ~ +3.3 分），两轮测量一致。

### 2.3 分离度与排序相关性（P0 新增分析）

按夹具配方把样本分成质量档（`weak 1 < real 2 < mixed 3 < equiv 4`），看各口径的中位 ATS：

| 质量档 | n | 期望质量 | v1 等权 | v2 分层 | v2 分层+语义 |
|---|---|---|---|---|---|
| weak | 2 | 1 | 41.0 | 41.0 | 41.0 |
| real | 3 | 2 | 52.0 | 54.0 | 54.0 |
| mixed | 5 | 3 | 54.0 | 57.0 | **67.0** |
| equiv | 20 | 4 | 54.0 | 57.0 | **67.0** |

| 指标 | v1 等权 | v2 分层 | v2 分层+语义 |
|---|---|---|---|
| Spearman(期望质量, ATS)，档位级 n=4 | +0.949 | +0.949 | +0.949 |
| Spearman(期望质量, ATS)，样本级 n=30 | +0.400 | +0.400 | **+0.415** |
| **有真实缺口的档位与"等价表述"档位的 ATS 差** | 0（54 vs 54） | 0（57 vs 57） | **13 分（67 − 54）** |

**诚实结论（重要，避免过度解读）**：

- **语义层的核心作用被验证了**：`mixed`（存在真实缺失）与 `equiv`（缺失项其实等价）在 `v1` 与 `v2` 分层下 ATS **完全相同**（54/54、57/57），系统无法区分这两类简历。接入语义校验后，两者拉开 **13 分**——这正是"假差距修正"要解决的问题。
- **但"排序相关性"没有改善**（+0.400 → +0.415，几乎无变化；档位级三者完全相同）。
  原因有二：① 20/30 份夹具属于同一档（`equiv`），档内高度同质，Spearman 对平级不敏感；
  ② **夹具存在"关键词贫乏"的系统性偏差**——`equiv` 夹具刻意只写 2 条等价表述，其余能力都不写，因此它们的规则覆盖率天然很低（覆盖 6–10/20），**被 ATS 压在地上**。真实简历不会这样写。
- 因此：**目前不能声称"分层或语义提升了排序质量"**。要检验这一点，必须换一批"能力覆盖面广、仅在个别项上存在假差距"的夹具。→ **已完成，见 [P2-b 排序验证夹具与结论](P2-b_排序验证夹具与结论.md)**：
  新夹具上 Spearman 为 v1 等权 **+0.859** / v2 分层 **+0.835** / 真实 LLM 语义 **+0.847**（含证据强度过滤）/ oracle 上界 **+0.980**。
  结论是"语义排序增益存在（+0.145 上界），但当前模型判断质量只能兑现其中一小部分"。

### 2.4 单份示例（`resume_00`，期望假差距 `分布式`）

```
missing: Go, Spring Cloud, Kubernetes, 微服务, 分布式, 高并发, 性能优化, 稳定性, 架构设计, 容器化, 开源
  real_gap  Go / Spring Cloud / Kubernetes / 高并发 / 容器化 / 开源   （证据留空，未编造）
  false_gap 微服务   ← "将单体应用按业务域拆为 6 个独立服务，跨服务调用全部走异步消息"

```

ATS：**59 → 63（仅分层）→ 76（分层+语义）**。

## 3. recall 未满的 2 例：**这正是 Agent 化的证据**

漏判的 2 例都是 `equiv` 中的 `架构设计`，模型判成了 `real_gap`。看简历原文：

> `- 参与订单中心方案设计，涉及模块划分与依赖治理。`

模型倾向保守——`参与`+`涉及` 的表述比"主导、设计"弱，它不愿认定为等价。**这个判断本身是合理的**（弱信号不轻易认定为等价，是 precision 优先的策略）。

但它同时说明：**单次调用没有"再看一眼"的能力**。它无法：
- 去检索"参与方案设计"是否算架构设计经验（`kb_search`）；
- 去读项目经历全文确认这个人是不是主导者（`read_section`）；
- 自己核对再下结论（`locate_quote` 自检 + 重试）。

**Agent 循环恰好提供这三件事。** 所以 P2 的验收标准里，"agentic 相比 single 的 recall 提升"有了一个具体的、可量化的标靶：**把这两例救回来 → recall 96.2%**。如果 agent 循环救不回来，那它就没有额外价值——这个实验设计是干净的。

## 4. precision 数字为什么不能用（以及怎么修）

严格 precision 30.3%（23/76）**不能作为质量结论**，因为：

**夹具的 `expected_false_gaps` 未穷举。** `PLAN` 对每个 `equiv` 只声明了 1 个设计目标，但模型在**同一份简历**里合理地识别出了更多等价（ATS 均值 +10 分不可能只来自 26 条声明项）。

证据：`resume_00` 声明 1 个（`分布式`），模型判了 5 个（+`微服务`/`性能优化`/`稳定性`/`架构设计`），而这 5 条的引文**全部真实可定位**且语义成立。

因此：
- `precision = 30.3%` 是**下界**，被 ground truth 的不完整压低了；
- 真正可信的是 **证据定位通过率 100%**（判定的证据没有一条是编的）。

**两种修法**（P2 之前做）：
1. 把夹具 post-pass 升级为"穷举式"：对每个 `missing` 关键词，用**独立模型**预标一次并人工抽检，形成完整 ground truth；
2. 或者收窄指标口径：只对"`PLAN` 声明的关键词"计算 precision/recall，其余单列为"额外发现（不计分）"。

## 5. 环境变更：移除耗尽额度的模型（2026-10-16）

**第 28 份夹具时 `qwen3.8-max` 免费额度耗尽**：

```
aliyun 403: {"error":{"message":"Free quota exhausted. To continue accessing the model
             on a paid basis, please add funds or disable the \"use free tier only\" mode"}}
```

**实测澄清（重要，更正初版结论）**：这次**没有**整体降级为 mock。逐份检查 30 份缓存：

| 实际服务的模型 | 份数 |
|---|---|
| `deepseek-v4-pro-0813` | **21** |
| `qwen3.8-max` | 9 |

即额度耗尽后，现有降级链**正常切到了同层的 `deepseek-v4-pro-0813`**，30 份**全部由 live 模型完成**，没有一份落在 mock。这也解释了 `resume_28`/`resume_29` 为何各产出 17 条判定且 `v2full == v2tier`（那两例本就没有声明假差距，不是降级）。

**处置（用户决定：先走离线缓存，删掉没钱那个模型）**：

| 动作 | 内容 |
|---|---|
| `.env` | 移除 `qwen3.8-max`：`ALIYUN_MODEL=deepseek-v4-pro-0813`，`ALIYUN_MODEL_FALLBACKS=qwen3.7-flash,qwen3.7-flash-2026-07-15` |
| 备份 | `backend/.env.bak-20261016`（并已加入 `.gitignore`：`backend/.env.bak*`） |
| 恢复方式 | 充值后把 `ALIYUN_MODEL` 改回 `qwen3.8-max`、放回 FALLBACKS 首位即可 |
| 新降级链 | `aliyun:deepseek-v4-pro-0813 → aliyun:qwen3.7-flash → aliyun:qwen3.7-flash-2026-07-15 → deepseek:deepseek-flash` |
| 评估脚本 | `eval_agentic.py` 默认引擎改为 **`cache`（离线复用，不调 API）**；要真实调用必须显式 `--engine single` |

**剩余可用额度**（实测）：`aliyun/deepseek-v4-pro-0813`、`aliyun/qwen3.7-flash`、`aliyun/qwen3.7-flash-2026-07-15`、`deepseek/deepseek-flash` 四个模型均可用；**只有 `qwen3.8-max` 不可用**。

**为什么移除而不是只降级**：留着它做阶梯首位，每次调用都要先白等 2 次重试（`LLM_MAX_RETRIES=2`）才降级，是纯粹的延迟与日志噪声。
