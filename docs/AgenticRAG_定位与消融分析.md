# Agentic RAG 定位与消融分析

> 分析日期：2026-10-22　｜　被测版本：`afd22e4`（+ 本地文档改动）
> 目的：回答一个关键质疑 —— **「Agentic RAG 比不过 fixed，是不是因为 fixed 里也用了大模型？如果 fixed 去掉大模型会怎样？」**
> 结论先行：**质疑的前半句是对的，后半句不能用来证明 Agentic RAG。**
> 正确结论是：**fixed + LLM 是强基线；去掉 LLM 会退化成关键词 ATS 工具；Agentic RAG 的价值不在「检索覆盖更多」，而在「自主取证 + 引用可校验 + 过程可解释」。**

---

## 1. 先确认事实：fixed 线里确实全是 LLM

fixed 不是「规则检索」，而是「**固定检索策略 + 8 个 LLM Agent**」：

| 节点 | fixed 线实际做什么 | 是否用 LLM |
|---|---|---|
| `parse` | 规则解析 + LLM 纠错/结构化 | ✅ |
| `jd_match` | LLM 判定关键词覆盖、假差距 | ✅ |
| `ats` / `impact` / `risk` | 三个 LLM Agent 并行分析 | ✅ |
| `suggestion` | LLM 逐条改写建议 | ✅ |
| `report` | LLM 生成摘要与叙述 | ✅ |
| `qc` | LLM 质检 + 规则否决 | ✅ |
| 分数 `compute_scores_deterministic` | **规则引擎确定性计算** | ❌（刻意不用 LLM） |

因此 `eval_rag` 的 fixed vs agentic 对比，**两臂用的是同一个模型、同一套分数**，唯一变量是：
**检索策略（一次性固定 query / top-5）** vs **Agent 自主多轮检索 + 工具调用 + 引用校验**。

这是一次**干净的「检索策略消融」**，不是「有没有 LLM」的对比。所以「Agentic 覆盖没赢 fixed」只能说明：
**在 55 个切片的知识库上，多轮检索没有比一次 top-5 捞到更多 gold** —— 不能说明 Agentic RAG 没有价值。

---

## 2. 如果 fixed 去掉大模型，会变成什么样？（已实测）

2026-10-22 18:53，用同一份弱简历、隔离库、**清空模型 Key 走 mock/规则模式**，实跑 fixed 流水线：

```
端到端 3.0s，8 个节点 tokens 全为 0，成本 ¥0
分数：overall 60 / ats 54 / impact 30 / clarity 95 / match 61 / risk 78
findings：5 条（LLM 版是 8 条）
建议：模板化（"补上规模与结果指标：日均调用量 / QPS"）
知识库引用：固定 top-3，无 findings 级引用与 provenance 校验
```

关键发现：

1. **分数几乎不变** —— 因为分数本来就由规则层算，LLM 不参与打分。
   所以「去掉 LLM」削掉的不是分数，而是**解释与建议**。
2. **findings 从 8 条掉到 5 条**，且全部是模板规则（关键词缺失、无量化、时间线空窗），
   没有语义假差距、没有上下文风险推理。
3. **建议质量断崖**：规则版只能套模板（"补指标"），不能针对这条经历写改写句。
4. **假差距检测归零**：P-1 基线里规则层的假差距 recall 就是 **0%**（定义上无法区分"真缺"与"同义表述"）；
   实测 `mixed`（有真缺口）与 `equiv`（其实是等价表述）两档 ATS **完全相同（54/54、57/57）**，
   接入 LLM 语义层后才拉开 **13 分**。
5. **解析鲁棒性下降**：全角数字、纯英文简历、多栏 PDF 等边界输入，规则层会静默解析失败或被压分
   （历史 B-3 缺陷就是靠 `analyze_guard` + LLM 兜底修的）。

**所以「无 LLM 的 fixed」不是一个产品形态，而是规则降级路径**（无 Key / 模型全挂时保命用）。
拿 Agentic RAG 去赢这个对手，等于用「有 LLM」赢「没 LLM」，**变量不是 Agentic，而是 LLM** —— 面试里会被一眼看穿。

## 3. 三层能力阶梯（现有数据能支撑的版本）

| 层级 | 语义假差距 recall | mixed vs equiv 区分 | 报告 findings / 建议 | 引用能力 | 单份成本 / 延迟 |
|---|---|---|---|---|---|
| **A. 规则-only**（fixed 去掉 LLM） | **0%**（规则无法判定） | **0 分**（54/54、57/57） | 5 条模板建议 | 固定 top-3，无结论级引用 | ~¥0 / **3.0s** |
| **B. fixed + LLM**（生产基线） | **88.5%**（P-1，单次调用） | **+13 分** | 8 条、贴合原文 | 3 条知识引用，无 findings 级 provenance | **¥0.0513 / 38.6s** |
| **C. Agentic + LLM**（项目主线） | 语义判定 90.3%（P2-c，旧模型） | 分数同 B（规则算分，Agent 不改分） | 8–14 条 + 逐条依据 | **14/14、12/12 引用通过校验**，findings 级引用 + 检索轨迹 | **¥0.4498 / 112.9s** |

> 口径说明：A 来自本轮 mock 实测 + P-1 基线；B 来自本轮 5 次实测；C 来自本轮 2 次实测 + P2-c/P3 历史评测。
> 表中「语义判定 90.3%」是旧模型上的历史数字，与 B 的 88.5% 不是同一模型/同一批夹具，**只能看方向，不能看差值**。

**这张表真正说明的事**：

- **LLM 是「建议质量」和「语义判断」的主驱动**（A→B 的跃迁），不是 Agentic RAG 的功劳；
- **Agentic RAG 的增量在 B→C**：检索从「一次固定 query」升级为「Agent 自主多轮 + 工具调用」，
  产出从「报告级 3 条引用」升级为「**findings 级、可逐字校验的引用 + 检索轨迹**」；
- **C 的分数与 B 相同**是设计使然：分数必须可回归，Agent 只补证据、不改分。
  所以任何「Agentic 更准」的说法都不成立；它更**可信、可解释、可审计**。

## 4. 为什么在当前知识库上，Agentic 覆盖没有赢 fixed

1. **知识库太小**：55 个切片，`top_k=5` 已经覆盖库容量的 9%；fixed 的一次 JD 宽 query 就能覆盖主要主题。
   Agentic 多轮检索的边际收益被「库本身很小」吃掉了。
2. **评测 gold 是按「规则层结论」推导的**：fixed 的宽 query 天然贴近这些结论；Agent 的窄 query 反而可能漏掉。
3. **两臂共用同一套 LLM 分析节点**：检索到的证据最终都要经过同一个分析模型；证据多一点少一点，
   在「结论级引用」出现之前，对最终报告的影响很小。
4. **55 片规模下，多轮检索的代价（3 轮、18 片、+32s、+50k tokens）换不来覆盖率提升** —— 这是实测结论，必须承认。

**这也解释了为什么本项目把 Agentic 定位为「能力增量」而不是「性能选项」**：
它现在的价值是**引用与可解释性**，不是覆盖率；覆盖率收益要等知识库规模上来才会出现。

## 5. 要真正证明 Agentic RAG，应该做哪些实验（下一步）

| # | 实验 | 现状 | 预期 |
|---|---|---|---|
| 1 | **同 LLM、检索策略消融**：fixed 一次 top-5 vs agentic 多轮 | ✅ 已做（10 例，v4 索引；fixed 88.0% vs agentic 87.1%） | 覆盖持平 → 证明「多轮检索不是万能药」 |
| 2 | **去掉 LLM 消融**：规则-only vs fixed+LLM | ✅ 已做（本轮 mock + P-1 历史） | 分数不变、建议质量断崖 → 证明 LLM 是主驱动 |
| 3 | **工具消融**：agentic 禁用 `kb_search` / `read_chunk` / `locate_quote` 各一组 | ❌ 未做 | 量化每个工具的边际贡献（引用通过率/轮次） |
| 4 | **知识库扩容**：55 → 500 / 2000 切片，重复实验 1 | ❌ 未做 | fixed 的 top-5 覆盖率触顶，agentic 多轮优势显现 |
| 5 | **多跳/异构证据子集**：需要「简历模板 + 岗位能力 + 合规」三类证据的 case | ❌ 未做 | fixed 单 query 难以同时覆盖，agentic 可规划 |
| 6 | **引用质量人工评估**：引用是否真的支撑结论（不只是逐字可定位） | ❌ 未做 | 从「引用可信」升级到「引用有用」 |

> 推荐在简历/面试里这样讲：
> **「我做了两组消融：同 LLM 下换检索策略，覆盖持平，说明多轮检索在 55 片小库上没有收益；
> 去掉 LLM 后报告退化为模板，说明 LLM 才是建议质量的主驱动。
> 所以我把 Agentic RAG 的价值定义为『自主取证 + 引用可校验 + 过程可解释』，
> 并用 14/14 引用校验和完整检索轨迹来证明它 —— 而不是虚构一个覆盖率提升。」**

## 6. 与 `eval_rag` 结论的一致性

| 指标 | fixed（1 次 top-5） | agentic（多轮） | 解读 |
|---|---|---|---|
| gold 覆盖（9/10 例，v4 索引） | 88.0% | 87.1% | 覆盖没有提升（55 片小库） |
| 至少引到 1 条 gold | — | 100% | 引用能力成立 |
| 引用逐字校验 | 无此能力 | 14/14、12/12 | **能力从无到有** |
| 轮次 / 成本 | 1 / ¥0.05 | 3.0 / ¥0.093（单例） | 约 2–9× 成本 |
| 检索轨迹可解释 | 固定 query，不可见 | 每轮自拟 query + 拦截方向 + 校验统计 | **可解释性从无到有** |

**结论：在当前规模，Agentic RAG 不赢覆盖、不赢分数；它赢的是「引用能力」与「过程可解释」。**
这不是失败，而是把价值主张说准了。

---

## 7. 产品与简历的定位建议

- **产品默认**：fixed（成本/延迟友好，覆盖已足够）；
- **Agentic 开关**：面向「需要审计/解释」的场景（HR 复核、面试辅导、答辩演示），
  或在知识库扩容后作为默认；
- **简历叙事**：把 Agentic RAG 作为**主线能力**（Agent 运行时、工具、预算、trace、引用校验），
  fixed 作为**强基线与降级路径**；永远不要把「规则-only」当作对比对象来证明 Agentic 更强。

> 一句话：**Agentic RAG 的价值不是「比 fixed 多捞几条 knowledge」，而是「让每条结论都有可验证的出处」。**
> 这正好是简历诊断最需要、也最难造假的能力。
