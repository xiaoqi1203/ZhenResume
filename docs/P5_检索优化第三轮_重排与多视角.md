# P5｜检索优化第三轮：重排与多视角（全部被实测否决）

> 日期：2026-10-21　｜　状态：**代码保留、默认不启用**
> 结论：**在 43 切片库上，单 query 全局排序的 89.2% 已接近上限；四种优化全部无提升。
> 真正的瓶颈不是检索算法，而是 gold 评测集没跟上库的增长。**

---

## 1. 这一轮做了什么

上一轮（扩库到 19 篇 / 43 切片）的结论是"库够大了，终于能测出优化效果"。
本轮据此实现并评测了四类方案：

| 方案 | 实现 | 零依赖？ |
|---|---|---|
| **BM25 重排** | `embeddings.bm25_scores()` + `rag.search(rerank=True)`，候选池 top_k×3 | ✅ 纯 Python |
| **MMR 去冗余** | `rag._mmr_select()`（token Jaccard 相似度） | ✅ 纯 Python |
| **多视角 query 融合** | `rag.perspective_queries()` + `rag.search_multi()`（RRF） | ✅ 无 LLM |
| **scope 融合**（上一轮） | `rag.search_scoped()` | ✅ 无 LLM |

### 为什么不用 cross-encoder

环境实测：`torch` / `transformers` / `sentence_transformers` / `numpy` / `sklearn`
**全部缺失**。装 torch 约 2GB，对当前 MVP 不成比例。BM25 在"短查询 + 短切片"场景下
是强基线，先用它把"重排到底有没有用"测清楚，再决定要不要引入重依赖。

| 臂 | recall@5 | Δ vs 基线 | scope 覆盖 | 耗时 |
|---|---|---|---|---|
| **基线（单 query 全局排序）** | **89.2%** | — | 2.00 | 213ms |

## 3. 为什么全都没用（三条根因，逐条有证据）

### 3.1 被漏掉的 gold 切片与 query **在语义上无关**

把没被召回的 gold 切片打出来看：

| gold 切片 | 内容 | 与 JD query 的关系 |
|---|---|---|
| `3bf866ba`（经历要点的黄金表达结构 #1） | "**禁用词清单**：负责、参与、协助、跟进、配合…" | 讲"怎么写"，**不含 JD 任何技能词** |
| `abd7488a`（ATS 关键词匹配 #0） | "主流 ATS 处理简历的流程：格式解析→字段抽取…" | 讲"机器怎么读"，**不含 JD 任何技能词** |

初排名次：前者 **25**、后者 **13**（全库 43 片）。

**单 query 无论怎么重排都排不上来 —— 信号根本不存在。** 这不是算法问题。
BM25 也一样：它只能重排"已经被召回进候选池且有词面重叠"的切片。

### 3.2 MMR 与 gold 的定义**直接冲突**

gold 的标注方式是"同一篇文档的多个切片"：
- 后端能力模型 #0 + #1
- 表达结构 #0 + #1
- ATS 机制 #0

MMR 的作用是**惩罚"与已选结果相似"的候选** —— 而 gold 本身就是"相似的那几片"。
所以 MMR 去重等于**按定义惩罚 gold**，58.3% 是必然结果，不是参数没调好。

### 3.3 强制多维度覆盖 = 按比例丢弃相关结果

`scope 融合` 与 `persp_only` 的 scope 覆盖都达到了 **4.00（满分）**，但 recall 崩到 30.8% / 61.7%。
原因：gold 集中在 `role` 与 `resume_template` 两类（共 5 篇自撰文档），
强制给 `industry` / `compliance` 留席位，等于从 top-5 里扣掉 1–2 个本该给 gold 的名额。

**覆盖面不是越多越好，而是"不要漏掉相关的那几类"。**

## 4. 最关键的发现：**gold 评测集没跟上库的增长**

这是本轮最有价值的产出，比任何一次调参都重要。

### 4.1 事实

| | 数量 |
|---|---|
| 当前知识库 | 19 篇 / **43 切片** |
| gold 标注覆盖的文档 | **5 篇**（后端能力模型、表达结构、ATS 机制等自撰规范） |
| **从未进入 gold 的文档** | **8 篇**（O*NET ×4、McMaster、Dartmouth、SocialTalent、EEOC） |

### 4.2 后果（两个方向都是坏的）

1. **recall 天花板被锁在旧文档上**：检索器把 O*NET 切片排到第 1 位，也不计分；
2. **任何"增加覆盖面"的改动都被惩罚**：O*NET 切片占了 top-k 名额却不计分 ——
   这正是 scope 融合（30.8%）与多视角（无提升）数字难看的主因之一。

### 4.3 一个反面验证

我试着用"O*NET 前 3 片 + McMaster 前 2 片"当新 gold，结果 recall 是 **0.00** ——
但 `base top5` 里明明有 O*NET 切片（第 2 位）。

原因：**机械取前 N 片不是 gold**。gold 的定义是"**真正能支撑该简历某条结论**的切片"，
这需要判断，不能按顺序截取。这恰好证明：**扩 gold 是人工标注工作，不能自动化。**

## 6. 结论与下一步

### 6.1 结论

**检索算法已不是瓶颈。** 在 43 切片、top_k=5 的设定下：
- 单 query 全局排序 89.2%，已经接近"gold 只覆盖 5 篇文档"这个评测框架的上限；
- 四种增加复杂度的手段（scope 融合 / BM25 重排 / MMR / 多视角）**全部无提升或有害**。

### 6.2 下一步（按性价比）

| 优先级 | 事项 | 理由 | 验证方式 |
|---|---|---|---|
| **P0** | **扩 gold 标注**：为每份简历，把 O*NET / McMaster / Dartmouth / EEOC 里"真正能支撑该结论"的切片标进 gold | 当前 recall 天花板是评测集造成的，不是检索器造成的 | 扩完后重跑 `eval_retrieval`，看基线是否变化 |
| **P0** | **扩评测集**：从 10 例扩到 30+ 例 | 10 例的均值方差太大，效应量被噪声淹没 | 看多轮运行的标准差 |
| **P1** | 检索缓存（同任务重复 query 只 embedding 一次） | W1 让检索调用变多，成本会放大 | 统计 embedding 调用次数 |
| **P2** | 若 gold 扩完、基线仍 <95%，再考虑 cross-encoder | 到那时才值得引入 2GB 依赖 | `eval_retrieval` 加 cross-encoder 臂 |
| ❌ 不做 | scope 融合 / MMR / 多视角作为默认路径 | 实测全部有害 | 数据见 §2 |

### 6.3 方法论沉淀（三轮失败的共同教训）

| 轮次 | 尝试 | 结果 | 教训 |
|---|---|---|---|
| 1 | scope 融合（每 scope 保底） | 89.2% → 58.3% | 强制覆盖会挤掉同文档的第二个 gold |
| 2 | 提示词要求"query 写宽" | 第 1 轮 55% → 41.7% | 指标噪声（σ=0.11–0.29）远大于效应 |
| 3 | BM25 / MMR / 多视角 | 全部无提升或有害 | **瓶颈在评测集，不在算法** |

**共同教训：先确认"瓶颈在哪一层"，再动手优化。** 三轮里有两次是在错误的层上优化
（检索算法），真正的问题一直在评测集与指标噪声上。
