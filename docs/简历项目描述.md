## 一、项目一句话

**ZhenResume（简甄）**：面向求职者与 HR 的 AI 简历诊断系统。FastAPI + LangGraph 多 Agent + RAG，
上传简历与 JD 后 60 秒内产出可定位、可执行的诊断报告；支持 HR 批量初筛、简历编辑器与分享导出。

## 二、简历条目（详细版，6 条）

1. **设计并实现 8-Agent 诊断流水线**（LangGraph 图编排，ats/impact/risk 三路并行），
   覆盖解析、岗位匹配、ATS 检测、影响力、风险、改写、报告与质检；真实模型 5 次实测
   **单份 38.6s（p95 41.8s）/ ¥0.0513**，满足「60 秒、0.5 元」验收线。
2. **用确定性规则引擎算分、Agent 只补证据**，解决 LLM 打分不可回归问题：同一简历重复诊断
   总分稳定（弱/中/强 = 60/85/91），并修复「摘要总分与展示总分不一致」「风险等级与红色条目冲突」
   等 4 类报告自相矛盾缺陷（一致性用例 20/20）。
3. **构建可校验的证据链**：每条红色风险绑定原文 `span + quote`；知识库引用在落库前做
   「chunk 存在 + quote 逐字可定位 + 本轮检索确实返回过」三重校验。实测拦截了模型编造的 chunk_id
   （分析 Agent 自身引用通过率仅 2/5–4/5），证据节点 14/14、12/12 引用全部通过校验。
4. **HR 批量初筛走 3 节点轻量图**：并发 50 下 **100 份 52.7s / 100% 成功 / ¥0.0184 每份**，
   成本仅为完整流水线的 35%；并给出「完整流水线外推 100 份 ≈82s 不达标」的量化取舍。
5. **以评测驱动检索优化**：自建 32 例、SE≈0.5pp 的检索评测集，验证「top_k 与注入 prompt 的前 3 条解耦」
   （前 3 条 recall 在 k=3–12 恒定），并用产品口径证伪 BM25 的 +8.2pp「显著收益」；
   同时定位到 embedding 换型会使历史检索指标整体漂移，建立「模型+索引版本」评测口径。
6. **完整工程化**：40+ REST 端点、175 项契约回归、55 项账号鉴权、74 项真实 HTTP 黑盒、
   SQLite/PostgreSQL 双存储、Celery+Redis 生产执行、Docker Compose 全栈、Next.js 前端
   （typecheck/lint/build 3/3）、SSE 真流式进度与分享/导出闭环。

## 四、STAR 面试稿（约 200 字）

- **S（背景）**：求职者拿到「ATS 匹配度 62 分」这类结论，不知道具体改哪句；HR 初筛又需要快速排序。
- **T（任务）**：做一个能在 60 秒内产出「可定位、可执行、可回归」诊断报告的 MVP，并支持 HR 批量初筛。
- **A（行动）**：用 LangGraph 编排 8 个 Agent、三路并行；分数由规则引擎确定性计算、LLM 只补建议；
  用「原文 span + quote + 知识库引用校验」保证证据可信；HR 场景单独设计 3 节点轻量图；
  通过契约回归与 32 例评测集持续验证，拒绝无稳定收益的检索改造。
- **R（结果）**：单份 38.6s / ¥0.05（真实模型 5 次），100 份 52.7s / 100% 成功；
  175 项契约回归全过；发现并修复报告自相矛盾、引用编造、SQLite 并发锁等真实缺陷。

## 五、三个可深聊的技术难点

### 1. SQLite 批量并发锁死 → 短事务 + 任务级并发
- 现象：legacy 引擎在 8 节点循环里持有一个长事务，批量 10 份 **9 份 `database is locked`，总墙钟 336s**。
- 处理：切 LangGraph 节点短事务 + 批量任务级 asyncio 并发；100 份 52.7s、零锁冲突。
- 收获：**先把事务边界画对，再谈并发**；数据库不是瓶颈，事务持有时间才是。

### 2. LLM 降级链的「最后一公里」
- 主模型 504/ReadTimeout 时自动切备用模型；全部失败时回落到规则引擎，仍产出契约合规报告。
- 实测发现：agentic 走 LangChain 兜底到 DeepSeek thinking 模型时，因未回传 `reasoning_content` 报 400。
- 收获：**降级链本身也要被测试**；兜底模型的协议差异（thinking、tool call、JSON mode）是隐藏故障源。

### 3. 评测指标与产品行为的因果链
- `recall@k` 看起来在提升，但产品只把前 3 条注入 prompt；实测前 3 条 recall 在 k=3–12 恒定。
- BM25 在 recall@8 上有 +8.2pp（统计显著），但对产品口径零收益；换 embedding 后甚至变负。
- 收获：**优化指标前先证明指标与用户看到的东西有因果关系**；显著性 ≠ 稳健性 ≠ 产品收益。

## 六、高频面试问答

| 问题 | 回答要点 |
|---|---|
| 为什么用 LangGraph，不用 Dify/Coze？ | 需要内嵌到 FastAPI、与业务表同库、可控节点级降级与预算；外部平台会多一层服务与状态同步成本 |
| 8 个 Agent 怎么划分？ | 按「输入解析 → 匹配 → 三维评估（可并行）→ 建议 → 报告 → 质检」职责切分，节点间只传结构化契约 |
| 怎么保证同一简历分数一致？ | 分数由规则引擎算，Agent 不参与；语义层只做「假差距修正」；跨 5 次实测 60/85/91 稳定 |
| 怎么防止模型编引用？ | 服务端 provenance 校验（chunk 存在 + quote 逐字定位 + 本轮检索返回过）；不通过直接丢弃 |
| 为什么换 PG + Redis + Celery 没变快？ | 单份 95% 时间在等 LLM；交错 A/B 显示栈开销仅 0.4–0.6s/份；换栈买到的是并发安全与可扩展 |
| Agentic RAG 成本 8.8×，值吗？ | 它把「结论级引用」从 0 做到 100%，是能力增量；但分数不变、慢 2.9×，所以默认关闭、单独定价 |
| 100 份 52.7s 怎么做到的？ | 3 节点轻量图 + 并发 50 + 每份仅 2 路并行；完整流水线外推 100 份约 82s，产品上初筛不需要 |
| 检索怎么评测？ | 32 例 v2 gold、embedding-only、同 k 对比 Δ 与 95%CI；另设「产品口径」脚本只看前 3 条 |
| 最大的技术风险是什么？ | 供应商抖动（同一天 35.9s→169.2s）与安全配置；前者靠超时/降级/告警，后者靠上线前加固 |
| 如果重做会怎么改？ | 更早建立真实用户评测集；把「配额/计费/审计」作为一等公民；观测 p95 而非均值 |

## 七、诚实边界（简历/面试不要说）

- ❌ 「Agentic RAG 让诊断更准」——实测 gold 覆盖 87.1% 未超过 fixed 88.0%，价值在引用能力。
- ❌ 「排序质量显著提升」——语义接入修正了分数低估，但 Spearman 未显著提升。
- ❌ 「100 份 ≤60s 是稳定 SLA」——余量仅 7.3s，供应商抖动会超时；应说「本机实测 52.7s」。
- ❌ 「成本 0.05 元是真实账单」——按忙时原价折算的保守上限；真实应付约 0.5×–1.0×。
- ❌ 「已生产可用」——当前是 MVP 演示配置，公网部署前需完成安全与配额加固（报告 §8.3）。
