## 一、项目一句话

**ZhenResume（简甄）**：以 **Agentic RAG** 为核心的 AI 简历诊断系统。
FastAPI + LangGraph 多 Agent + RAG，Agent 自主多轮检索、调用工具取证，
把每条诊断结论绑定到简历原文与知识库切片，并经过服务端逐字校验；
上传简历 + JD 后 60 秒内产出可定位、可执行、可审计的报告。

**一行版（简历项目名下方）**：
`FastAPI · LangGraph Agentic RAG · 多轮检索 + 工具调用 · 引用 provenance 校验 · Next.js 14 · 实测 38.6s / ¥0.05 每份`

## 二、简历条目（Agentic RAG 主线，6 条）

1. **设计并实现 Agentic RAG 运行时**（`app/agentic/`）：AgentSpec + BaseAgent，
   统一封装**预算（轮次/工具调用上限）、trace、缓存、模型回退、强制收尾**；
   把 4 个分析节点（jd_match / ats / impact / risk）从「单次 LLM 调用」升级为
   **自主决定检索方向、调用 9 只读工具、多轮取证**的 Agent 循环，新增 qc 后的
   `agentic_evidence` 证据节点，实现「结论 → 引用 → 原文」的闭环。
2. **构建可校验的引用链路**：引用落库前做「chunk 存在 + quote 逐字可定位 + 本轮检索确实返回过」三重校验；
   实测 `agentic_evidence` **14/14、12/12 引用全部通过**，同时发现分析 Agent 自身引用通过率仅 2/5–4/5
   （模型会编 chunk_id），证明**服务端 provenance 校验是必需的最后一道闸**，而不是可选项。
3. **用消融实验说清 Agentic RAG 的价值边界**（不是堆指标）：
   - 同 LLM 下对比检索策略：fixed 一次 top-5 vs agentic 多轮（32 例检索评测 + 10 例端到端），
     **gold 覆盖 88.0% vs 87.1%** → 在 55 切片小库上多轮检索没有覆盖收益；
   - 去掉 LLM 的规则-only 版（本轮 mock 实测）：**语义假差距 recall 0%**、mixed/equiv 两档 ATS 完全相同（0 分差），
     说明 LLM 才是「建议质量」的主驱动；
   - 结论：Agentic RAG 的增量是**自主取证、引用可校验、检索过程可解释**，不是分数或覆盖率。
4. **8-Agent 诊断流水线**（LangGraph，ats/impact/risk 三路并行）：真实模型 5 次实测
   **单份 38.6s（p95 41.8s）/ ¥0.0513**；分数由规则引擎确定性计算，
   同一简历重复诊断稳定（60/85/91），并修复 4 类报告自相矛盾缺陷（一致性 20/20）。
5. **HR 批量初筛走 3 节点轻量图**：并发 50 下 **100 份 52.7s / 100% 成功 / ¥0.0184 每份**，
   成本仅为完整流水线 35%；给出「完整流水线外推 100 份 ≈82s 不达标」的量化取舍。
6. **完整工程闭环**：40+ REST 端点、175 项契约回归、55 项账号鉴权、74 项真实 HTTP 黑盒；
   SQLite/PostgreSQL 双存储、Celery + Redis、Docker Compose 全栈、Next.js 前端（typecheck/lint/build 3/3）、
   SSE 真流式进度与分享/导出闭环。

## 四、STAR 面试稿（Agentic RAG 主线，约 220 字）

- **S**：简历诊断产品都在给「结论」，但没人能证明结论有依据；模型还会编造引用。
- **T**：做一个「每条结论都可追溯、检索过程可解释」的诊断系统，并量化 Agentic RAG 到底值不值。
- **A**：自研 Agent 运行时（预算/工具/trace/回退），把 4 个分析节点改成自主多轮检索 + 9 只读工具；
  引用落库前做 chunk/quote/来源三重校验；同时设计两组消融：
  同 LLM 下换检索策略、以及在规则-only 版上验证 LLM 的作用，避免把「LLM 的功劳」算给 Agentic。
- **R**：引用校验 14/14、12/12 通过，检索轨迹可回放；单份 38.6s / ¥0.05，批量 100 份 52.7s；
  明确结论是「Agentic 不提升覆盖率，提升的是可信度与可解释性」，并把这个边界写进了团队文档。

## 五、三个可深聊的技术难点

### 1. Agent 循环的预算与收尾（不是「调个 prompt」）
- 问题：Agent 会无限检索/无限调工具；实测自然收敛需 5–6 次模型往返、31 次工具调用。
- 处理：轮次 + 工具调用双上限、每轮预算、强制收尾（收到 finish 立即停）、
  trace 记录每轮 query/tool/耗时；超限不是报错，而是降级为「无引用报告」。
- 收获：**Agent 工程的核心是「有界」**——没有预算的 Agent 只是不可控的循环。

### 2. 引用造假：模型会编 chunk_id
- 现象：分析 Agent 自己的引用通过率只有 2/5–4/5，失败原因集中在「引用了本轮检索没返回过的 chunk」。
- 处理：服务端 provenance 校验（chunk 存在 + quote 逐字定位 + 本轮检索返回过），
  不通过直接丢弃；`agentic_evidence` 节点因此做到 14/14、12/12 全过。
- 收获：**「模型说它引用了」不等于「它真的引用了」**；引用必须由服务端复核。

### 3. 评测因果：为什么「Agentic 比不过 fixed」不是失败
- 现象：fixed 也全程用 LLM，所以 fixed vs agentic 是「检索策略」消融，不是「有没有 LLM」。
- 处理：拆成三组实验：同 LLM 换检索策略、去掉 LLM 的规则版、以及产品口径（前 3 条）评测；
  发现 gold 覆盖无差异，但引用能力从 0 → 100%。
- 收获：**显著性 ≠ 稳健性 ≠ 产品收益**；先证明指标与用户看到的东西有因果关系，再谈优化。

## 六、高频面试问答（Agentic RAG 版）

| 问题 | 回答要点 |
|---|---|
| 为什么说 fixed 也是 LLM？那 Agentic 赢在哪？ | fixed = 固定检索 + 8 个 LLM Agent；Agentic 的变量是检索策略 + 工具 + 引用校验。覆盖没赢，赢在「自主取证 + 引用可校验 + 过程可解释」 |
| 如果 fixed 去掉大模型会怎样？ | 退化为规则 ATS：3.0s/¥0、5 条模板建议、假差距 recall 0%、mixed/equiv 分数无差异；这不是产品形态，是降级路径。拿它当对手是「有 LLM 赢没 LLM」，变量不对 |
| 那你怎么证明 Agentic 的价值？ | 引用能力从 0 到 100%（14/14、12/12 校验通过）、检索轨迹可回放、工具调用可审计；同时诚实承认 55 片小库上覆盖无提升 |
| 为什么分数不随 Agentic 变？ | 分数必须可回归，由规则引擎算；Agent 只补证据与建议，不改分。这是设计约束，不是缺陷 |
| Agent 怎么防止跑飞/烧钱？ | 轮次与工具双上限、预算、trace、强制收尾、模型回退；默认 fixed，Agentic 按需开启 |
| 为什么不用 Dify/Coze？ | 需要内嵌 FastAPI、与业务表同库、节点级预算/回退/引用校验；外部平台多一层状态同步 |
| 成本 0.45 元/份值吗？ | 引用与审计场景值；默认 fixed（0.05 元）覆盖 90% 需求，Agentic 作为高端/审计模式 |
| 如果知识库扩到 2000 片呢？ | 这才是 Agentic 的主场：fixed 的 top-5 会触顶，多轮检索 + 多工具规划才有覆盖收益；这是下一步实验 |
| 你踩过最大的坑？ | agentic 兜底到 DeepSeek thinking 模型时未回传 `reasoning_content` 导致 400；降级链本身也要被测试 |
| 如果重做会怎么改？ | 更早做 KB 扩容/工具消融实验；把引用质量从「可定位」升级到「人工评估有用」 |

## 七、诚实边界（简历/面试不要说）

- ❌ 「Agentic RAG 让诊断更准 / 覆盖率更高」——实测 55 片库上覆盖 87.1% vs fixed 88.0%，分数由规则算。
- ❌ 「去掉 LLM 的 fixed 比 Agentic 差」——那是「有 LLM vs 没 LLM」，不是 Agentic 的贡献。
- ❌ 「100 份 ≤60s 是稳定 SLA」——余量 7.3s，供应商抖动会超时；应说「本机实测 52.7s」。
- ❌ 「成本 0.05 元是真实账单」——按忙时原价折算的保守上限；真实应付约 0.5×–1.0×。
- ❌ 「已生产可用」——当前是 MVP 演示配置，公网部署前需完成安全与配额加固（报告 §8.3）。
