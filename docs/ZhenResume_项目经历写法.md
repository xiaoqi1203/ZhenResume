# 把这个项目写成简历亮点：ZhenResume 项目经历写法

> 用途：把 `E:\ZhenResume` 这一个仓库，写成简历上**能被追问、追问了还能答得漂亮**的项目经历。
> 原则：面试官不关心你用了什么技术，只关心三件事 —— **你做了什么决策、怎么证明它对、结果改善了多少**。技术栈罗列是减分项。

---

## 1. 先备好"可量化的事实清单"（全部来自仓库，不是编的）

写简历之前先建这张表。没有数字的 bullet 一律不写。

| 事实 | 数字 / 结论 | 出处 |
|---|---|---|
| 端到端契约自检 | **174 项断言**，一条命令覆盖 上传 → 解析 → 8-Agent 诊断 → 报告 → 支付 → 知识库检索 → HR 批量 → 隐私删除 → DOCX/PDF 抽取回归 | `backend/scripts/verify.py` |
| 诊断流水线 | **8 个节点**（parse / jd_match / ats / impact / risk / suggestion / report / qc），顺序即冻结契约 | `agents/__init__.py`、`docs/api-contract.md §4.2` |
| 单步可观测 | 每步落 **tokens / cost / latency / status**，任务级 `progress`、`current_step` 可轮询 | `workflow_steps` 表、`GET /tasks/{id}` |
| 零依赖可跑通 | **没有 API Key 也能产出契约合规的完整报告**（live → 重试 2 次 → 规则引擎回落，步骤标记 `degraded`） | `services/llm.py` 三重降级链 |
| 分数可复现 | 五维评分由确定性公式算出，**同一简历两次诊断分数完全一致**（有断言保护） | `services/analyze.py::compute_scores` |
| 证据可追溯 | 模型只输出引文，**字符区间由后端在原文里重新定位**；定位不到的红色风险被质检强制降级 | `services/evidence.py`、`qc_agent.py` |
| 公平性 | 歧视性内容**双层拦截**（风险 Agent + 质检 Agent），公平性通过率 100% 是验收项 | `risk_agent.py`、`qc_agent.py` |
| 建议质量 | 报告**始终 ≥5 条**可执行建议；不足时补"简历里真实存在的优点"（green）而不是编造问题 | `suggestion_agent._ensure_minimum` |
| 成本 | 单份报告 API 成本 **≤ 0.5 元**（按可配置单价核算，看板可见 `cost_per_report`） | `services/cost.py`、`/admin/metrics` |
| 编辑器与导出 | **4 套模板** + 结构化编辑器 + **Markdown / DOCX / PDF** 三格式导出；编辑器产出的简历与上传的简历走**同一条流水线**（无特殊分支） | `app/editor`、`resume_render.py` |
| 性能 | mock 模式全链路约 **1 秒**；live 模式目标「上传后 60 秒内出报告」 | README、`aaa.md §4/§5` |
| 数据模型 | 15 张 ORM 表（用户/简历/JD/任务/报告/发现项/工作流步骤/知识库/支付/订阅/反馈/审计/HR 批次/Prompt） | `models.py` |
| 架构可回退 | 编排层是可替换点：手写状态机与 LangGraph 共用同一批 `services/*`，**一个环境变量切换** | `WORKFLOW_ENGINE` 开关 |

> 用法：简历上写 2–3 条 bullet，每条挑 1–2 个数字。**不要全堆上去**——堆多了像 README 搬运。

---

## 2. 三段式模板（每条 bullet 的骨架）

```
【难点/背景】 → 【我的决策 + 为什么这么做】 → 【验证方式 + 结果数字】
```

判断一条 bullet 是否合格：把技术名词全部删掉，还剩不剩信息量？剩不下就是不合格。

---

## 3. 可直接套用的写法（按岗位三选一）

### 3.1 主推版（AI 应用 / 后端岗）

> **简历诊断服务（独立完成 · FastAPI + Next.js + LangGraph）**
> - 设计并实现 **8 节点诊断流水线**（解析 / JD 匹配 / ATS / 影响力 / 风险 / 建议 / 报告合成 / 质检），节点间以显式 JSON 状态传递，每步落 tokens、成本、耗时；配套 **174 项端到端契约自检**，一条命令覆盖上传、诊断、报告、支付、知识库、HR 批量、隐私删除全链路。
> - 为支撑「改完简历重新诊断、对比分数变化」这一核心卖点，**刻意不让 LLM 打分**：五维分由确定性公式计算，并用「引文必须能在原文定位、否则红色风险强制降级」的质检闸门保证结论可追溯，实现同一简历两次诊断分数完全一致。
> - 编排层做成**可回退的替换点**：MVP 先用手写状态机上线（节点签名与 LangGraph 对齐），再用契约测试锁住行为，最后替换为 LangGraph 1.2（断点续跑 / 三路并行 / 节点级重试），**替换前后 174 项断言全绿**。

### 3.2 决策能力版（面试偏架构时用这条压轴）

> - **框架选型**：评估过低代码平台（Dify）方案 —— 因其确定性资产（评分、证据定位）必须外移、workflow run 不幂等、业务状态与运行日志割裂、以及多租户授权条款，最终选择全代码路线（LangGraph + pgvector + Langfuse），并把选型结果做成 **legacy / langgraph 双引擎开关**，而不是一次性重写。

### 3.3 质量工程版（测试 / 平台岗）

> - 建立**契约冻结 + 行为回归**的工作方式：接口契约文档先冻结（含 12 类错误码与 8 个步骤名的顺序），再用 174 项端到端断言把"主链路真的能跑"变成一条命令；任何重构（引擎替换、模块拆分、检索升级）都以这份断言全绿为唯一验收口径。

## 4. 面试官一定会追问的 8 个问题（这才是"更优"的真正门槛）

简历写得好只是拿到提问权；**答得上来才加分**。把下面这些准备成 30 秒版本：

| 追问 | 一句话答案（都可以从这个仓库里举证） |
|---|---|
| 为什么不用现成的低代码平台？ | 评分与证据定位是确定性资产，外移到平台后不可回归；平台 run 不幂等、没有 async 模式，长流程无法重试；业务状态和运行日志会分家。 |
| 8 个 Agent 为什么这么拆？ | 每个节点只做一件事、输出可校验的 JSON、独立可观测（tokens/成本/耗时），且顺序本身就是对外契约（前端时间线硬编码这 8 个步名）。 |
| 为什么不让 LLM 打分？ | 一旦 LLM 打分，"改完再测、对比分数"这个卖点就是假的 —— 同一份简历两次诊断必须同分。 |
| 怎么防止模型编造？ | 四层：系统提示明确禁止编造 + 证据链只信原文定位 + 缺数据用 `[补充指标：…]` 占位而不是编数字 + 质检对不合规条目降级/剔除。 |
| 模型挂了怎么办？ | 三重降级：重试 2 次 → 回落该节点的规则引擎实现并标记 `degraded`（不静默）→ 只有 critical 的解析节点失败才终止任务。没有 Key 时整条链路照样跑。 |
| 成本怎么控？ | 每个节点上报 tokens/cost，看板按步骤聚合 `cost_per_report`；单价走配置；并发改造后仍按节点记账。 |
| 并发怎么保证不破坏确定性？ | 三件事：并行节点只写各自的批次字段（同一 superstep 写同一 channel 会直接报错）、归并顺序固定、进度由"已完成契约步去重 / 8"推导而非自增。 |
| 你怎么证明改动没破坏东西？ | 174 项契约断言 + 金标快照（评分/引文定位/解析基线/检索排序）+ 双引擎逐位比对分数。 |

## 5. 反面清单（这么写会被扣分）

| 别这么写 | 为什么 |
|---|---|
| "使用 FastAPI、LangGraph、PostgreSQL、Redis、Celery、Docker 等技术栈" | 技术栈堆砌，零信息量；面试官会挑一个问深，答不上就全崩 |
| "实现了简历诊断功能" | 没有决策、没有数字 |
| "精通 LangGraph / 精通 Agent 开发" | 换成"用 LangGraph 1.2 实现断点续跑与并行扇出，并以 174 项契约测试保证替换前后行为等价" |
| 编造用户量、准确率、QPS | 一问就穿；用真实数字（174 项断言、8 节点、≤0.5 元/份、≥5 条建议）反而更有说服力 |
| 把"我参与了"写成一长串功能点 | 挑 2–3 个"有决策、有验证"的点写透，比列 10 个功能强 |

## 6. 可选：把项目拆成两条经历

如果目标是投**全栈 / 前端**，或者简历太空，可以拆成两条：

- **主线**：简历诊断流水线（AI 应用 / 后端）—— 8-Agent、确定性评分、证据链、降级链、契约自检。
- **副线**：简历编辑器与多格式导出（全栈）—— 结构化编辑器 + 实时预览 + 草稿自动保存；**DOCX 刻意保持单栏纯段落（不用表格/文本框，因为那是 ATS 解析失败的头号原因）**；编辑器内容与上传文档在诊断流水线中等价（有专门断言）。

副线特别适合展示"**产品判断力**"：为什么 DOCX 不用表格、为什么 PDF 由 DOCX 转出、为什么下载必须用 `fetch` 带 `X-Device-Id`（浏览器原生导航不带自定义请求头，会导致归属校验失败 → 导出 404）。这类"踩过才知道"的细节，比任何技术名词都值钱。

## 附：如果问的其实是"产品侧的建议怎么写更优"

（上面若答非所问，看这段 —— 这是让**报告里给用户的改写建议**更好的方向，都能落在现有代码上。）

1. **强制 STAR 化**：现状 `rewritten_text` 是"改写句"，可升级为"动词 + 对象 + 指标占位 + 结果"的结构化模板（`analyze.py` 已有强/弱动词表与 `QUANT_SIGNAL_RE`，扩展成生成式规则即可）。
2. **指标占位要具体到可填**：不要写 `[补充指标：…]`，而是 `[补充：优化后 P99 延迟从 __ms 降到 __ms]` —— 提示用户填什么，比让他自己想有效得多。
3. **与 JD 术语对齐**：`jd_match_agent` 已算出 `missing_keywords` 与 `false_gaps`，把这部分直接变成"把简历里的『性能优化』改成 JD 里的『高并发性能调优』"这类**逐词替换建议**，命中率远高于泛泛而谈。
4. **按行业/岗位分层**：`knowledge_docs.scope` 已支持 `role` / `industry`，可为不同 `role_family` 准备不同的动词与量化范式，让建议"像这个行业的人写的"。
5. **每条建议附"改完能拿多少分"**：现在报告有总分与维度分，可以给出"这条改完预计 +X 分"的估算（用 `compute_scores` 在改动后的模拟输入上重跑一遍即可 —— 这正是"确定性评分"除了可对比之外的第二个红利）。
