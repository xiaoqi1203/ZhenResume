## 1. 为什么需要重做夹具（P-1 夹具的根本缺陷）

P-1 夹具测出了 recall（88.5%）与证据定位通过率（100%），但**测不出排序质量**：

- 20/30 份 `equiv` 夹具只写 2 条等价表述，**其余 11 项能力全都不提** → 规则覆盖率天然很低，所有 `equiv` 夹具的 ATS 都被压在 54 分，**与 5 份 `mixed`（含真实缺口）完全相同**；
- ground truth 只声明 1 个假差距、未穷举 → precision 不可用（30.3% 是假的下界）；
- 结果：Spearman 仅 +0.400，且三种口径几乎无差异（+0.400 → +0.415）。

**根本原因不是"分层或语义没用"，而是夹具把"能力覆盖度"这个变量给压死了。**

## 2. 新夹具的设计（`sort_fixtures`）

### 2.1 一个必须避开的坑

第一版设计里，技能栏写了「分布式、高并发、微服务…」这些词 —— 规则层做**子串匹配**，
无论工作经历里有没有真的做过，都会判"已覆盖" → **所有夹具 ATS 顶到满分，排序无从谈起**。

因此最终版规定：**技能栏只列技术名词**（`Java、Spring Boot、Spring Cloud、MySQL、Redis、Kafka、Docker、Git、Linux`），
八个能力维度**只出现在工作经历的要点里**，使"覆盖与否"完全由要点内容决定。

### 2.2 结构

- **8 个能力维度**，每维两种写法：`literal`（含目标词 → 规则层判覆盖）/ `equiv`（不含目标词但表达同一能力 → 规则层判缺失，语义层应判表述差异）；
- **4 组配方**（每组 8 份，共 32 份），按设计覆盖度递减：A ≈ 100% / B ≈ 66% / C ≈ 40% / D ≈ 19%；
- ground truth **逐维度完整声明**：`designed_literal` / `designed_equiv` / `designed_real_gaps`，
  并用 `make_sort_fixtures.py` 的 post-pass 与规则层对齐（只保留规则层确实判缺失的项）。

### 2.3 顺带发现的两个真实隐患

1. **子串匹配把 "MySQL" 当成了 "SQL"**：7 份夹具中设计为真缺失的 `SQL` 未被规则层判缺失，
   因为 `"sql" in "mysql"` 成立。这属于真实的口径缺陷（会 MySQL ≠ 会 SQL），
   ground truth 已自动剔除这些项，**但生产判断仍受影响**，建议在 `scoring_version=v3` 时改为词边界匹配。
2. `io.TextIOWrapper(sys.stdout.buffer, ...)` 会接管 buffer 所有权，包装对象回收时关闭 stdout
   （报 `I/O operation on closed file`）——已统一改为 `sys.stdout.reconfigure(...)`。

## 3. 结论（oracle 上界 vs 现状）

`oracle` 模式把 ground truth 的等价项**直接当作已覆盖**（且为每项在原文中取一段真实引文），
代表"语义判断 100% 正确"的理论上界；`--engine rule` 代表当前线上（无语义）。

| 组 | n | 设计覆盖均值 | ATS v1 等权 | ATS v2 分层 | ATS v2 + **oracle 语义** | 语义救回幅度 |
|---|---|---|---|---|---|---|
| A | 8 | 7.75 | 71.0 | 76.0 | **85.0** | **+9.0** |
| B | 8 | 5.25 | 70.5 | 74.5 | **82.0** | **+7.5** |
| C | 8 | 3.25 | 68.2 | 72.2 | **75.8** | **+3.5** |
| D | 8 | 1.50 | 62.2 | 66.2 | **67.8** | **+1.5** |

| 指标 | v1 等权（现状） | v2 分层 | **v2 分层 + oracle 语义** |
|---|---|---|---|
| 组间单调性（A≥B≥C≥D） | ✅ | ✅ | ✅ |
| **Spearman(设计覆盖项数, ATS)** | +0.859 | +0.835 | **+0.980** |
| 假差距 recall | 0%（无语义） | 0% | 100%（定义） |
| 真差距误判 | 0 | 0 | 0 |

### 三条关键结论

1. **排序增益第一次被量化**：接入语义判断后，`Spearman` 由 **+0.835（分层）提升到 +0.980**，
   离完全单调只差 0.02。这是"语义层有价值"的直接证据 —— 而 P-1 夹具测不出这个差异。
2. **救回幅度按质量单调递减**（A +9.0 > B +7.5 > C +3.5 > D +1.5），与设计一致：
   候选人能力越扎实，其"用不同措辞表达"的项越多，语义层能救回的也越多。
   **这正是"分数应当反映真实质量"所要求的方向** —— 而不是所有简历一律加分。
3. **分层加权对排序没有增益**（+0.859 → +0.835，略降）。这与 P-1 的观察一致：
   分层的价值在于**惩罚分配更合理**（缺加分项不应与缺核心项同罚），而不是提升排序相关性。
   若要验证分层的排序价值，需要另设"缺核心 vs 缺加分"配比不同的夹具组。

## 4. 真实 LLM 的结果：一个重要的负面发现

用 `qwen3.8-flash` 跑同一批夹具（32 份，`--engine single`）：

| 口径 | Spearman(设计覆盖, ATS) | 假差距 recall | **误判真差距** | 结论 |
|---|---|---|---|---|
| v1 等权（现状） | +0.859 | 0% | 0 | 基线 |
| v2 分层 | +0.835 | 0% | 0 | 分层不改排序 |
| **v2 + 真实 LLM（仅硬校验）** | **+0.756** ❌ | **100%** | **81 条** | **排序反而被拉低** |
| v2 + 真实 LLM + **证据强度过滤** | **+0.847** ✅ | 90.3% | **48 条** | 超过基线 |
| v2 + oracle（语义 100% 正确） | **+0.980** | 100% | 0 | 上界 |

### 4.1 根因：`locate_quote` 只能证明"引文不是编的"，证明不了"引文够不够"

逐条查看 81 条误判，问题不是编造引文，而是**弱证据 / 跨维度挪用**：

```
[误判] 微服务    quote: "Spring Cloud"                     理由：Spring Cloud 是微服务框架，具备该技能即代表具备微服务能力
[误判] 容器化    quote: "Docker"                           理由：掌握 Docker 即具备容器化部署能力
[误判] 高并发    quote: "数据库高峰期 CPU 从 85% 降至 50%"   理由：处理高峰期负载隐含了应对高并发的经验
[误判] 稳定性    quote: "协助排查线上环境问题"                理由：排查线上问题服务于系统稳定运行
[误判] 架构设计  quote: "设计分布式缓存与消息队列方案"        理由：设计分布式组件属于后端架构设计范畴
```

**81 条误判的引文中位长度仅 19 字**，大量是技能栏里的**裸技术名词**。
硬校验（`locate_quote`）全部放行——因为它们确实是原文片段。这正是改动说明书 §6.4 记录过的
`容器化 → "Docker"` 边界案例，**在真实数据上它不是一个孤例，而是主要失败模式**。

更值得注意的是救回幅度：A +9.0 / B +10.8 / C +10.8 / D +10.6 —— **四组几乎相同**，
说明模型对"真缺失"和"等价表述"不做区分，而是**只要语料风格像就一律救回**（过度救回）。
这解释了为什么排序相关性不升反降。

### 4.2 验证过的缓解措施：证据强度过滤

在硬校验之上叠加一条**确定性**规则：引文必须**出自工作经历要点**（以 `- ` 开头的行）且长度 ≥ 10 字。
即排除"技能栏裸词"与"过短碎片"。

| | 误判真差距 | recall | Spearman |
|---|---|---|---|
| 仅硬校验 | 81 | 100% | +0.756 |
| **+ 证据强度过滤** | **48** | 90.3% | **+0.847** |

**收益**：误判减少 41%，排序相关性由"低于基线"回到"高于基线"（+0.835 → +0.847），recall 仅损失 9.7 个百分点。
**这验证了延期中的 R2（语义限幅）思路的方向是对的——只是手段应该是"证据强度"而不是"分数限幅"**。

### 4.3 剩余 48 条误判：纯推理质量问题，无法用规则解决

剩下的误判引文**确实出自经历要点且长度足够**，只是内容与结论不匹配（例如把"设计分布式缓存方案"当作"架构设计"的证据）。
这类需要的是**模型自己多查一步**：

- 去检索"设计缓存方案是否算架构设计经验"（`kb_search`）；
- 去读项目经历全文判断是不是主导者（`read_section`）；
- 自己核对再下结论（`locate_quote` 自检 + 重试）。

**这正是 P2-c（Agent 工具循环）要补的部分，而且现在有了精确的标靶**：

> `v2-full` 的 Spearman 目前 **+0.847**，oracle 上界 **+0.980**，
> **差距 +0.133 就是"推理质量"的可量化空间**。
> 若 Agent 循环不能把 +0.847 往 +0.980 推近，它就不值得引入。

## 5. P2-a：单次调用版判定引擎（对照臂）已建成

> 代码：`app/services/semantic_agent.py` → `run_semantic_single_pass()`
> 运行：`python -m scripts.eval_sort --engine semantic`（判定结果缓存在 `eval/runs/cache_sort/`）

**设计**（与 P2-c 的 Agent 循环严格同协议，唯一变量是"轮次与自主性"）：

| | P2-a（本模块） | P2-c（待做，LangChain 封装） |
|---|---|---|
| 协议 | 原生 function calling | 同 |
| 工具 | `agent_tools.TOOL_SPECS`（同 7 个） | 同 |
| 工具轮次 | **固定 1 轮**（模型要什么给什么，另加兜底强制读 `work`） | 模型自主决定轮次与顺序 |
| 终止 | 固定（拿到工具结果即收尾） | 由模型输出 `finish` 决定 |
| 自检重试 | 无 | 可用 `locate_quote` 自检后重试 |
| 校验 / 算分 | `services/semantic` + `compute_scores_deterministic` | **完全相同，一字不改** |

### 5.1 全量结果（32 份夹具，`qwen3.8-flash`）

| 组 | 设计覆盖均值 | ATS v1 | ATS v2 分层 | **ATS v2 + P2-a 引擎** | 救回幅度 |
|---|---|---|---|---|---|
| A | 7.75 | 71.0 | 76.0 | **84.5** | +8.5 |
| B | 5.25 | 70.5 | 74.5 | **84.1** | +9.6 |
| C | 3.25 | 68.2 | 72.2 | **81.5** | +9.2 |
| D | 1.50 | 62.2 | 66.2 | **75.1** | +8.9 |

| 口径 | Spearman(设计覆盖, ATS) | 假差距 recall | 误判真差距 |
|---|---|---|---|
| v1 等权 | +0.859 | 0% | 0 |
| v2 分层 | +0.835 | 0% | 0 |
| 提示词 JSON（P2-b 的旧口径，`--engine cache`） | +0.847 | 90.3% | 48 |
| **P2-a：单次调用 + 工具（`--engine semantic`）** | **+0.838** | **94.4%** | **56** |
| oracle 上界 | **+0.980** | 100% | 0 |

### 5.2 两个必须记住的结论

1. **工具让 recall 上升但没让排序变好**：recall 90.3% → **94.4%**（模型确实读到了更多依据），
   但误判 48 → **56**，Spearman 停在 **+0.838**（与分层的 +0.835 几乎相同）。
   → **瓶颈不是"没看到材料"，而是"看到了也判断不准"**。这条排除了"补信息"这条改进路径。
2. **救回幅度四组几乎相同**（+8.5 / +9.6 / +9.2 / +8.9），说明模型**不做难度区分**：
   对覆盖度只有 19% 的 D 组也照样大量救回。这与 P2-b 中"提示词 JSON 版"的观察一致，
   且在给了工具之后**没有改善** → 过度救回是**模型判断倾向**问题，不是信息问题。

### 5.3 对 P2-c 的精确要求

> P2-a 已把"单次调用 + 工具"的天花板钉在 **+0.838**，oracle 上界是 **+0.980**。
> **P2-c（Agent 工具循环）必须证明自己能把这 +0.142 的差距实质性地缩小**，
> 手段只能是"自检与重规划"：让模型用 `locate_quote` 核验自己准备引用的片段、
> 用 `kb_search`/`read_section` 在证据不足时补查、并在多轮之间修正判断。
> 若做不到，诚实的结论就是「这个任务不需要 Agent 循环」——那也是一个有效的研究结论。

### 5.4 顺带修正的一处提示词缺陷

首版 P2-a 引擎没把 JD 原文/简历原文放进工具调用提示词，模型只调了 `rubric_get` + `jd_requirements`
就下结论，**把 9 项全判成真差距**（recall 0%）。修法两点：① 提示词里直接给出 JD 与简历原文；
② 若模型未请求 `read_section`，引擎**兜底补一次**（否则对照臂测的是"没看材料"而不是"推理能力"）。
修正后同一夹具 4/4 全中、0 误判。

## 6. P2-c：LangChain 封装的 Agent 工具循环

> 代码：`backend/app/services/agent_langchain.py` → `run_semantic_agent_langchain()`
> 运行：`python -m scripts.eval_sort --engine langchain`（判定缓存在 `eval/runs/cache_sort/*.lc.*.json`）
> 状态：**架构已跑通、行为已验证；量化对比因额度事故被污染，需重跑（见 §6.4）**

### 6.1 实现（用 LangChain 的哪些部分）

| 用 | 说明 |
|---|---|
| `langchain.agents.create_agent` | 标准「模型→工具→回灌」状态图；**每轮自主决定调什么、调几个** |
| `StructuredTool` + Pydantic args_schema | 7 个工具直接包装 `agent_tools.ToolRunner`（与 P2-a 同一执行器，口径一致） |
| `finish` 工具 | 结构化出口：`judgments: list[{keyword,verdict,resume_quote,reason}]` |
| `ModelCallLimitMiddleware` / `ToolCallLimitMiddleware` | 预算硬上限（实测自然收敛 5–6 次模型往返、约 30 次工具调用） |
| `ModelFallbackMiddleware` | 主模型失败时按供应商×模型阶梯回退 |
| 递归上限兜底 | 撞上限时用最后状态**强制收尾**，不丢已有成果、不静默 |

**不用**：`with_structured_output`（DashScope 的 `json_schema` 支持不确定，而 tool calling 已实测可用）、
LangSmith tracing（会外发简历原文）。**校验仍走 `services/semantic`，LangChain 不改变可信边界。**

### 6.2 实测的 Agent 行为（32 份，这是架构成立的直接证据）

| 指标 | 均值 | 范围 |
|---|---|---|
| 模型往返 | **9.3** | 5–12 |
| 工具调用 | **16.6** | 7–27 |
| 检索轮次（kb_search） | 2.0 | 0–5 |
| **`locate_quote` 自检** | **2.5** | 0–6 |
| tokens | 33,722 | 16k–56k |
| 成本 | ¥0.08/份 | ¥0.04–0.13 |

**32 份里有 20 份主动做了 `locate_quote` 自检**，且工具序列表现出明显的"先读材料 → 批量核实 →
查行业基准 → 自检引文 → finish"的自主规划。典型轨迹：

```
第1轮 jd_requirements + 3×read_section
第2轮 18×resume_search（一次性批量核实全部关键词）
第3轮 4×kb_search
第4轮 4×locate_quote（自检）
第5轮 finish
```

**修复过的问题（都有实测依据）**：
1. `run_limit=16` 的 ToolCallLimit 会把 31 次工具调用**截断在 finish 之前**，判定全丢
   → 预算改为 `max_steps=16` / `max_tool_calls=60`；
2. `recursion_limit` 按 `2×预算+10` 太小（部分夹具需 23+ superstep）→ 改为流式取值 + 捕获
   `GraphRecursionError` + 上限放宽到 `4×预算+20`，撞限时强制收尾而不是抛异常中断整轮评测；
3. 部分夹具陷入"反复调同一工具"的死循环 → 提示词改为**明确 3 轮工具调用上限**并
   要求**批量**核实，`sort_D02` 由 18 次往返/超时收敛为 11 次往返/正常 finish。

### 6.3 结果：**架构成立，但质量尚未超过 P2-a**

| 口径 | Spearman | recall | 误判 |
|---|---|---|---|
| v2 分层（无语义） | +0.835 | 0% | 0 |
| **P2-a：单次调用 + 工具** | **+0.838** | **94.4%** | **56** |
| **P2-c：LangChain Agent（本次）** | **+0.729** | **61.1%** | **25** |
| oracle 上界 | +0.980 | 100% | 0 |

**这个数字不可直接采信**，原因见 §6.4。可观察到的方向性变化：
- **误判真差距 56 → 25（大幅下降）**——自检机制起了作用，救回更谨慎；
- 但 **recall 94.4% → 61.1%（大幅下降）**——救回不足，原因是 32 份里有 17 份是
  "预算耗尽后强制收尾"，且 10 份是在弱模型上跑的。

### 6.4 ⚠️ 评测污染：一天之内 3 个模型额度耗尽

跑全量评测期间按时间顺序发生：

| 时间 | 事件 |
|---|---|
| 10:31 | `qwen3.8-flash` → **403 Free quota exhausted**（前一个已耗尽的是 `qwen3.8-max`） |
| 10:54 | `deepseek-v4-pro-0813` → **403**（跑到第 22/32 份时） |
| 之后 | 主模型降级为 `qwen3.7-flash`（能力明显更弱），补完剩余 10 份 |

因此那 32 份结果里：**22 份由 `deepseek-v4-pro-0813` 判定、10 份由 `qwen3.7-flash` 判定**，
**且 P2-a 基线（+0.838）是在 `qwen3.8-flash` 上测的**。三者不同模型 → **横向比较不成立**。

**结论：P2-c 的"架构与行为"已验证；"质量是否优于 P2-a"必须等额度恢复后用同一模型重跑两臂。**
重跑成本估算：两个引擎各 32 份 ≈ 40 分钟、¥3–5。

### 6.5 已可确认的代价

| | P2-a 单次调用 | P2-c Agent 循环 |
|---|---|---|
| 模型往返 | 2 | **9.3**（约 4.7×） |
| tokens/份 | ~3,000 | **33,722**（约 11×） |
| 成本/份 | ¥0.005 | **¥0.08**（约 16×） |
| 延迟/份 | ~7 s | **~35 s**（约 5×） |

> 换句话说：Agent 循环用 **16 倍成本、5 倍延迟**换取"主动自检"。它是否值得，
> 取决于能否把误判降下来同时不牺牲 recall —— 这正是待重跑验证的核心。

## 7. 下一步
