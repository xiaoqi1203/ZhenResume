# P3｜Agentic RAG 检索评测与结论

> 代码：`backend/app/agentic/`（运行时 + 知识库证据 Agent）、`backend/scripts/eval_rag.py`
> 开关：`WORKFLOW_MODE=fixed|agentic`（**只影响单份诊断**，HR 批量恒为 fixed）
> 结论：**Agent 检索有正向增益（+4.1pp gold 覆盖），但真正的确定性优势是"结论级引用"——固定链路完全产不出来。**

---

## 1. 评测设计

同一批夹具（10 份简历 × 同一个后端 JD）、同一个知识库（11 篇文档 / 16 个切片）、同一套 gold 标注。

| | fixed 臂（现状） | agentic 臂（本次） |
|---|---|---|
| 检索时机 | 进图前**一次** | Agent 自主决定（0–4 轮） |
| query | `rag.build_query` = JD 标题/技能/关键词 + 简历技能（**JD 驱动**） | 模型按"证据需求"自拟（**结论驱动**） |
| 检索量 | `top_k=5` 固定 | 按需，可 `read_chunk` 下钻全文 |
| 引用 | **无 finding 级引用**（只有报告级 top-3 元数据） | finding 级 `{chunk_id, quote}` + 服务端逐字校验 |

**gold 标注**：每份简历产出 6–8 条规则层结论（多为"缺某关键词""只写职责没量化"），
把它们**真正能支撑的知识库切片**标为 gold（后端能力模型 / 量化标准 / 表达结构 / ATS 机制），每例 3–4 条。

指标：
- `gold_recall`：gold 切片被检索到的比例（0–1）；
- `citation_gold_rate`：Agent 引用落在 gold 的比例（宽口径，一条结论常有多条合理依据）；
- `至少引用到 1 条 gold`：该案例是否至少有一条引用是"引到点子上"的；
- `verified_rate`：服务端校验（quote 能否在切片中逐字定位）。

## 2. 结果（两轮独立运行，结论一致）

| 指标 | 固定检索 | Agent 多轮检索 | 判断 |
|---|---|---|---|
| **gold 覆盖（并集口径）** | **89.2%** | **96.7%** | ⚠️ 见 §2.1：**预算不对等，不能直接比** |
| **gold 覆盖（第 1 轮 / 同预算）** | **89.2%** | **55.0%** | ❌ **Agent 单轮更差**（这是 2026-10-21 新增口径后发现的真实结论） |
| 单案例胜/平/负（并集） | — | **3 胜 / 6 平 / 1 负** | ⚠️ 有增益但不稳定 |
| 至少引用到 1 条 gold | 0%（无引用能力） | **100%** | ✅ 能力差异 |
| 引用逐字校验通过 | — | **97–100%** | ✅ 引用可信 |
| 轮次 | 1 次 | 3.0–3.9 轮 | — |
| 成本 / 延迟 | ≈0（仅 embedding） | **¥0.07–0.09 / 23–28s** | ❌ 约 20×（但绝对值小） |

两轮运行的汇总数字：第一轮 61.7% / 61.7%（修复前，见 §3 的 bug）、第二轮 89.2% / 93.3%、第三轮 89.2% / 93.3%。
2026-10-21 用对齐口径重跑：固定 89.2% / 并集 96.7% / **第 1 轮 55.0%**。

### 2.1 ⚠️ 口径修正（2026-10-21，必读）

**原文档的「+4.1pp」是预算不对等的产物。** fixed 臂只检索 **1 次 top_k=5**，
agentic 臂是多轮检索的**并集**（实测每例取回 **8.0 个切片**）——多取 3 个切片再比覆盖，
本身就该更高，那不是"检索更聪明"的证据。

对齐口径后得到一个**更不利、但更真实**的结论：

| 口径 | 固定 | Agent | 差值 |
|---|---|---|---|
| 并集（预算不对等） | 89.2% | 96.7% | +7.5pp |
| **第 1 轮（同预算：都只检索 1 次）** | **89.2%** | **55.0%** | **−34.2pp** |

**为什么 Agent 单轮反而差**（不是 bug，是两种 query 策略的固有差异）：
- fixed 的 `rag.build_query()` 是 **JD 驱动的宽 query**（岗位名 + 6 个核心技能 + 6 个关键词 +
  简历 8 个技能，拼成 600 字）——它天然覆盖 gold 标注的那几类文档；
- Agent 按**结论需求自拟窄 query**（「后端工程师能力模型 分层 核心能力要求」），
  命中更精准但**覆盖面窄**，第 1 轮通常只查 1–2 个方向，gold 里另外两类自然没被覆盖。

**因此正确的表述是**：Agent 的检索增益**全部来自"多轮"**（补查不同方向），
不是来自"单次 query 更准"。这也解释了为什么增益集中在需要 `resume_template` 依据的案例
（A05 / D02 / D06）——那些文档 JD 驱动的宽 query 不指向，必须多轮才覆盖到。

> 这个结论对产品方向有直接影响：**如果要提升单轮质量，该做的是 query 改写/扩展
> 或 rerank，而不是继续加轮次**。加轮次只提升覆盖率，成本线性增长。

## 3. 评测中发现的真实产品 bug（已修复）

> **`rag.search(role_family=...)` 是硬过滤 `WHERE role_family = 目标族`，但
> `compliance / industry / resume_template` 三类文档的 `role_family` 是 `general`。**
>
> 后果：只要调用方传了 `role_family`，**"表达结构 / ATS 机制 / 公平性红线"永远检索不到**。
> 更糟的是它伪装成模型问题——Agent 会如实报告"resume_template 与 compliance 域检索为空，
> 故不引用"，看起来像模型不努力，实际是检索器把这类知识过滤掉了。

修复：过滤条件改为 `role_family IN (目标族, 'general', NULL)`。
修复后同一批 query 立刻能召回 general 文档（实测"简历量化表达标准"能命中《经历要点的黄金表达结构》）。

**这是本轮最有价值的产出之一**：它说明"Agent 表现不好"要先排除"工具本身坏了"。

## 4. 另一处改进：检索规划清单

第一轮评测中 `rag_D04` 回退（gold 覆盖 1.00 → 0.33）：Agent 的 query 全落在"量化/ATS/关键词"，
**漏了"岗位能力基准"方向**，所以没检索到后端能力模型切片。

修法：系统提示词增加**三类依据必须覆盖**的清单（只要与 findings 相关就必须各查一次）：
A. 岗位能力基准；B. 表达与量化规范；C. ATS 机制 / 合规红线。
修复后 `D04` 恢复 1.00；但 `A03` 在另一轮出现同类漏检，说明**检索规划仍有随机性**（诚实记录，不掩饰）。

## 5. 结论（诚实版，2026-10-21 修正）

1. **检索广度**：并集口径 +7.5pp（89.2% → 96.7%），但**预算不对等**（取回 8.0 条 vs 5 条）。
   同预算（都只检索 1 次）下 Agent 只有 **55.0%**，**比固定检索差 34.2pp**。
   → 准确表述：**Agent 的增益全部来自"多轮补查不同方向"，不是"单次 query 更准"。**
   在 16 切片的库上，这个增益的绝对空间本来就小；库越大、越跨域，预期收益越大。
2. **引用能力**：固定链路**完全不具备** finding 级引用（0%），Agent 做到 **100% 案例至少引到 1 条 gold、
   97–100% 引用逐字通过校验**——这是"能力从无到有"，不是指标微调。
   **这是本项目 Agentic RAG 唯一站得住的强项。**
3. **可解释性**：报告页能看到 Agent 自己拟定的检索方向、被预算拦下的方向、哪些方向没命中所以不引用，
   这是 `fixed` 链路给不出的东西，也是本项目"Agentic RAG"最直观的展示。
4. **代价**：每份 +¥0.07–0.09 / +23–28s；且 Agent 失败时降级为"无引用"，不影响报告产出与评分。
5. **方向修正**：继续加轮次只提升覆盖率、成本线性增长。**要提升单轮质量，query 改写/扩展
   与 rerank 才是杠杆** —— 但下面 §5.1 记录了两次尝试都失败的实测结果。

### 5.1 两次尝试提升单轮检索，均被实测否决（2026-10-21）

| 尝试 | 做法 | 实测结果 | 判定 |
|---|---|---|---|
| **scope-aware RRF 融合** | `rag.search_scoped`：同一 query 在 4 个 scope 内各排序 → RRF 融合（含"每 scope 保底 1 席"变体） | 检索器级（`eval_retrieval`，10 例 recall@5）：**宽 query 89.2% → 58.3%（−30.8pp）**；真实链路第 1 轮 55.0% → 58.3%（+3.3pp，但在噪声范围内，见下） | ❌ **不合入默认路径**。代码保留为 `search_scoped`（已评测、暂不启用） |
| **提示词要求写宽 query** | 在 `_OUTPUT_RULES` 加"一次 query 带 2–3 个维度" | 第 1 轮 55.0% → 41.7%（反向） | ❌ 已回退 |

**为什么 scope 融合会把宽 query 打坏**：gold 切片集中在 2 个文档（能力模型 2 个切片 +
表达结构 1 个），而强制 4 类各占一席会把 2 个名额送给 industry/compliance（不在 gold 里）。
在 `top_k=5` 的预算下，这是**结构性**冲突，不是调参能解决的。
→ **覆盖面不是越多越好，而是"不要漏掉相关的那几类"。**

### 5.2 ⚠️ 重要：`first_round_recall` 噪声过大，不可单独用于裁决

同一个代码、同一批 case，三次独立运行的第 1 轮 gold 覆盖分别是
**55.0% / 58.3% / 41.7%**；单例区间 **0.00–0.67**，标准差 **0.11–0.29**。

原因：第 1 轮只有 1 个 query，模型选哪个检索方向高度随机，而 gold 只标了 3–4 个切片。
**效应量（几个 pp）远小于噪声（几十 pp）**，所以这个指标**不能**用来判断"检索改动是否有效"。

要裁决检索器改动，请用 **`scripts/eval_retrieval.py`**（检索器级、固定 query、无模型随机性）。
它给出的稳定数字是：宽 query 全局排序 **89.2%**，这是当前的上限。

> 这条方法论教训比任何一次优化都重要：**先确认指标的噪声，再相信指标的变化。**

## 6. 复现方式

```bash
cd backend
python -m scripts.eval_rag              # 10 个案例全跑（约 4 分钟、约 ¥0.6）
python -m scripts.eval_rag --limit 3    # 快速验证
python -m scripts.eval_retrieval        # 检索器级对照（秒级、零 LLM，用于裁决检索改动）
python -m scripts.smoke_agentic_report  # 端到端：agentic 模式下 8 步契约 + 引用挂载
python -m scripts.eval_driven_analysis  # W1：检索是否在驱动分析（分析阶段引用覆盖率）
```

结果文件：`backend/eval/runs/` 下 `eval_rag_*.json`、`eval_retrieval_*.json`、`eval_driven_*.json`（gitignored）。
